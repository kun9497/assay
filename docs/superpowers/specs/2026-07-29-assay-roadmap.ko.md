# assay — 아키텍처와 로드맵

*[English](2026-07-29-assay-roadmap.md) · 한국어*

**작성일:** 2026-07-29
**상태:** 합의됨. 스캐폴드의 최초 서술을 대체함.

프로젝트 전체의 기준 설계 문서입니다. 개별 슬라이스는 각자의 구현 계획을 갖고, 이 문서는 **이
시스템이 무엇이고, 왜 이런 모양이며, 어떤 순서로 만들어지는지**를 기록합니다.

미룬 작업, 알려진 함정, 미검증 가정은
[`../../deferred-decisions.ko.md`](../../deferred-decisions.ko.md)에 있습니다.

---

## 1. 목표

컨테이너 이미지, 바이너리, 디렉터리, SBOM을 받아 거기 영향을 주는 알려진 취약점을 보고하는 단일
도구. 인벤토리 생성, 취약점 데이터베이스 구축, 그리고 둘의 매칭을 모두 포함합니다.

anchore 생태계에서는 이것이 세 개의 별도 프로젝트입니다. `syft`가 인벤토리를 만들고,
`vunnel` + `grype-db`가 데이터베이스를 만들고, `grype`가 매칭합니다. assay는 셋 다 합니다.

**개인 프로젝트이고, 취약점 스캐너가 어떻게 동작하는지를 끝에서 끝까지 직접 만들어보며 배우려고
시작했습니다.** 기존 스캐너들은 훌륭하고 충분히 검증되어 있습니다. 프로덕션에서는 그것들을 쓰십시오.
여기 있는 무엇도 그것들을 대체하려 하지 않습니다.

KISA/KNVD를 일급 provider로 삼는 데서 시작했습니다. 첫 조사(2026-08-02)는 그것이 성립하지
않는다고 결론지었는데, **그 결론은 틀린 게시판을 재서 나온 것입니다.** KNVD 자체 공개(173건, 국내
상용 소프트웨어)를 봤고, 보안공지(2,422건, CVE 키, Apache·OpenSSL 등)를 보지 않았습니다. 슬라이스
5에서 정정했습니다. KISA는 독립 매칭 소스가 아니지만 CVE 기반 보강 조인은 걸리며, 표본 3건은 셋 다
assay가 Alpine `apache2`와 `openssl`에 대해 이미 가지고 있는 권고였습니다.

실제로 만들어진 것, 그리고 아래 설계 목표가 봉사하는 것은, **자신 있게 틀린 답을 내지 않는
스캐너**입니다. 모든 finding이 왜 매칭됐는지 말하고, 평가하지 못한 것을 말하고, 스캔 중에는 취약점
데이터를 절대 받아오지 않습니다.

설계 목표, 우선순위 순: **설명 가능할 것**, **오프라인 동작**, **지루한 출력**(결정적이고,
diff 가능하고, CI 친화적으로).

### 비목표

설정 오류 스캔, 시크릿 스캔, IaC, 쿠버네티스 보안 태세 — trivy가 확장해 간 방향들입니다. 취약점
매칭과 공유하는 코드가 거의 없어서, 포함한다는 건 **같은 바이너리 안에 다른 도구를 하나 더 넣는
것**과 같습니다.

## 2. 결정들

각 결정은 근거를 함께 기록합니다. 근거가 있어야 나중에 개정할 수 있기 때문입니다.

### D1 — OSV를 정규화 대상으로 삼는다

권고는 OSV 형태로 저장합니다. `affected[].ranges[]`가 `introduced` / `fixed` 이벤트를 담습니다.

대안은 업스트림 피드를 직접 수집해 우리가 정규화하는 것이었습니다(NVD의 CPE match 범위, OVAL
조건 트리, 배포판 secdb 포맷 등). **소스마다 범위 표현이 다르고, 정규화 계층이 스캐너보다
커집니다.** anchore가 `vunnel`과 `grype-db`를 별도 리포지터리로 분리한 이유가 이것입니다.

검증된 정규화 대상을 재사용하는 편이 새로 만드는 것보다 낫습니다. OSV는 언어 생태계 커버리지도
강한데, 첫 슬라이스가 바로 거기입니다.

grype의 사전 빌드 데이터베이스를 읽는 방안은 배제했습니다. 그 스키마는 anchore의 내부 계약이라
메이저 버전마다 바뀌고, 결정적으로 **우리가 소유하지 않은 스키마에는 우리 소스를 넣을 수
없습니다.** KISA가 이 안을 탈락시킵니다.

### D2 — Provider 추상화를 첫날부터 둔다

KNVD 데이터가 OSV 형식으로 오지 않을 것이므로 수집과 정규화가 어느 정도는 불가피합니다.
`Provider` 인터페이스를 두면 OSV는 거의 통과에 가까운 구현체가 되고 KISA는 두 번째 구현체가
됩니다. 모든 업스트림 피드를 직접 만드는 데 발을 담그지 않고도요.

### D3 — KISA는 매칭 소스가 아니라 우선 보강이다

OSV로 매칭된 finding이 CVE ID 조인을 통해 한국어 설명, KISA 심각도, KNVD 링크를 가져옵니다.
KVE 항목이 자체적으로 finding을 만들지는 않습니다.

**조인은 `aliases`와 `upstream`을 모두 읽어야 합니다.** OSV 1.7 레코드는 CVE 링크를 `aliases`가
아니라 `upstream`에 담습니다. 표본으로 확인한 Alpine 레코드는 `"upstream":["CVE-2006-20001"]`을
갖고 `aliases`는 아예 없었습니다. 한 필드만 읽으면 **조인이 조용히 실패합니다.** 보강에서는 이게
최악의 실패 양상입니다 — finding은 그냥 한국어 데이터 없이 나타나고, 아무것도 오류를 보고하지
않습니다.

KNVD 권고 상당수가 국산 상용 소프트웨어를 산문으로 기술합니다. 생태계도, purl도, 패키지 이름도
없습니다. 패키지 매칭이 아니라 CPE식 *제품* 매칭이죠. 현재 타깃과도 안 맞습니다. 컨테이너
이미지와 소스 트리에 한컴오피스는 없으니까요. 승격 경로를 기록해 둔 채 미룹니다.

### D4 — 로컬 저장소는 bbolt

접근 패턴은 `(ecosystem, name)`에 의한 점 조회이고, 패키지 수만큼 반복됩니다. range scan도,
join도, 집계도 없습니다. **순수 key-value이고 SQL이 사줄 것이 없습니다.**

Makefile의 `CGO_ENABLED=0`이 `mattn/go-sqlite3`를 배제합니다. 남는 SQLite 선택지인
`modernc.org/sqlite`는 C를 Go로 기계 번역한 것이라, **`require` 블록이 아예 없는 `go.mod`에
넣기엔 매우 큰 의존성**입니다.

SQLite의 실질적 우위는 디버깅 하나입니다(개발 중 `sqlite3 db "select ..."`). 그건 `assay db
inspect`로 회수할 수 있고, 어차피 계획된 explain 모드와 겹칩니다. trivy도 같은 접근 패턴에서 같은
판단을 했습니다.

`Store`가 작은 인터페이스라, 이 판단이 틀렸다면 되돌릴 수 있습니다.

### D5 — 경로에 스키마 버전을 둔다

`<cache>/assay/db/v7/vulnerability.db`. 스키마가 바뀌면 마이그레이션 코드를 쓰는 대신 새
디렉터리에 다시 빌드합니다. **사용자가 한 명인 프로젝트에서 마이그레이션 코드는 부채입니다.**

### D6 — 배포판 패키지는 릴리스를 키에 포함한다

생태계 키는 `Alpine`이 아니라 `Alpine:v3.19`입니다. 패키지의 수정 버전이 릴리스마다 다르므로
릴리스가 조회 키의 일부입니다. OSV가 배포판 데이터를 분할하는 방식과도 일치합니다.

### D7 — 배포판은 패키지가 아니라 타깃에 속한다

*이미지*가 Alpine 3.19인 것이지 그 안의 패키지가 그런 게 아닙니다. `Target.Distro`는
`/etc/os-release`에서 한 번 읽어 내부의 모든 OS 패키지에 적용됩니다.

### D8 — `Package.Source`가 소스 패키지를 담는다

배포판 권고는 **소스** 패키지 기준으로 작성되지만 설치된 것은 **바이너리** 패키지입니다:

```
advisory:  source package  openssl     < 1.1.1n-0+deb11u3   vulnerable
installed: binary package  libssl1.1     1.1.1n-0+deb11u1
```

`libssl1.1`을 조회하면 아무것도 안 나옵니다. 매칭하려면 그것의 소스가 `openssl`이라는 걸 알아야
합니다. 이게 없으면 실패는 오탐이 아니라 **미탐**입니다 — 조용하고 훨씬 위험합니다. grype의 dpkg
matcher에서 가져왔습니다.

**이건 Debian과 RHEL만이 아니라 Alpine에도 적용됩니다.** 표본 OSV 레코드가
`"purl":"pkg:apk/alpine/apache2?arch=source"`를 담고 있습니다. Alpine 권고도 소스 기준입니다.
Alpine이 첫 배포판(슬라이스 2)이므로, **간접 매칭은 나중 배포판 작업으로 미룰 수 있는 게 아니라
거기서 필요합니다.**

채우는 방법은 cataloger마다 다릅니다. dpkg는 `/var/lib/dpkg/status`에 `Source:`를, apk는
`/lib/apk/db/installed`에 `o:`(origin)를 노출합니다.

### D9 — 버전 비교는 생태계별로 유지한다

Debian의 epoch, RPM의 release 순서, semver의 pre-release 우선순위, Maven의 정렬 규칙이 실제로
서로 어긋납니다. 공유 `compareVersions`는 이 설계가 피하려는 바로 그 버그입니다.

`Comparer`는 `int`이 아니라 `(int, error)`를 반환합니다. 실제 시스템의 버전 문자열은 때때로 형식이
깨져 있고, **파싱 불가능한 버전을 조용히 "취약하지 않음"으로 처리하면 그것이 미탐입니다.** 에러는
건너뛴 패키지와 그 개수로 표면화되며, 절대 클린 결과가 되지 않습니다.

### D10 — `Finding`이 `Evidence`를 담는다

설명 가능성이 목표 1번입니다. 근거가 타입 안에 없으면 로그 줄에 흩어지고, 그건 사실상 없는
것입니다.

### D11 — 종료 코드 우선순위는 계약이다

```
2 (could not run / cannot be trusted)  >  1 (findings at or above --fail-on)  >  0 (clean)
```

**신뢰할 수 없는 결과가 결과의 내용보다 우선합니다.** 종료 코드는 CLI 계약이라 나중에 바꾸면 남의
CI가 깨집니다. 그래서 이를 필요로 하는 강제 기능이 미뤄져 있음에도 지금 고정합니다.

### D12 — 신선도는 로컬 빌드 시각이 아니라 업스트림 데이터로 잰다

`Provenance.DataAsOf`가 **업스트림 데이터가 언제 기준인지**를 기록하며, 이는 로컬 데이터베이스를
조립한 시각인 `Meta.BuiltAt`과 별개입니다.

빌드 시각은 엉뚱한 것을 잽니다. 3개월 된 스냅샷을 서빙하는 미러에서 오늘 받아오면 빌드 시각은
오늘이 되고, 빌드 시각 기반 신선도 검사는 **한 분기 묵은 데이터를 최신이라고 보고합니다.**
에어갭 동작은 명시된 목표이지 예외 케이스가 아니므로, 이건 첫 빌드부터 맞아야 합니다.

나이 *강제*는 미뤘지만, 그것을 가능하게 하는 메타데이터는 미루지 않았습니다. 나중에 추가하려면
데이터베이스를 다시 빌드해야 하기 때문입니다.

### D13 — Provider는 업스트림 레코드를 무손실로 저장하고, 파생값은 조회 시점에 계산한다

예를 들어 심각도 밴드는 빌드 시점에 박아 넣는 대신 저장된 CVSS 벡터에서 뽑습니다. 이러면 **"지금
필요한 필드를 저장 안 했으니 데이터베이스를 다시 빌드하자"는 상황이 대부분 사라집니다.** 이 규모에서
저장 용량은 제약이 아닙니다.

### D14 — 스캔은 절대 취약점 데이터를 받아오지 않는다

권고 데이터를 받아오는 명령은 `assay db update` 하나뿐입니다. 데이터베이스가 없거나 스키마가
맞지 않으면 안내와 함께 종료 코드 2를 냅니다. **자동 다운로드도, 조용한 빈 결과도 없습니다.**

**슬라이스 2b에서 의도적으로 좁혔습니다.** 원래 문구는 "스캔 경로는 절대 네트워크를 건드리지
않는다"였는데, `assay scan alpine:3.19`가 이를 지킬 수 없습니다 — 이미지를 받아오는 것 자체가
스캔 경로의 네트워크 호출입니다. 이 규칙이 지키려던 것은 **소켓이 아니라 데이터베이스**입니다.
권고 데이터를 조용히 받아오는 스캐너는 결과를 재현할 수도 감사할 수도 없고, 그것은 여전히
금지입니다.

좁힌 규칙이 여전히 보장하는 것:

- **스캔 중에는 어떤 권고 데이터도 받아오지 않습니다.** 오래되었거나 없는 데이터베이스는
  에러이지, 스캔이 뒤에서 고쳐주는 대상이 아닙니다.
- **로컬 대상 스캔은 네트워크 호출이 전혀 없습니다.** SBOM 파일, `docker-archive:` tarball,
  `oci-dir:` layout은 완전히 오프라인이며, 이것이 에어갭 경로입니다.
- **대상만, 그것도 대상이 원격일 때만 받아옵니다.** 사용자가 입력한 인자에 그대로 드러납니다 —
  `alpine:3.19`은 외부로 나가고 `docker-archive:alpine.tar`은 나가지 않습니다.

### D15 — 악성 패키지 신고는 제외하되, `Advisory.Kind`는 제외하지 않는다

OSV에는 `MAL-*` 레코드가 있습니다. 패키지가 취약점을 포함한다가 아니라 패키지 자체가
**악성코드**라는 신고입니다. 실제 덤프로 측정한 결과 데이터의 압도적 다수를 차지합니다
(§3의 *측정된 데이터 규모* 참조).

제외하면 슬라이스 1 데이터베이스가 약 430 MB에서 약 86 MB로 줄어듭니다.

지금 제외하는 이유는 중요하지 않아서가 아니라 **성격이 다른 finding 클래스**이기 때문입니다.
CVSS 심각도가 없으므로 `--fail-on`이 아무 의미를 갖지 못하고, 올바른 보고는 심각도 밴드가 아니라
"지금 제거하라"입니다. 제대로 지원한다는 건 두 번째 finding 클래스를 설계한다는 뜻이고, 그건
슬라이스 1의 일이 아닙니다.

`Advisory.Kind`는 그럼에도 지금 넣습니다. 필드를 나중에 추가하면 데이터베이스를 다시 빌드해야
하니까요. Provider가 이 값을 설정하고, 현재 필터는 `KindVulnerability`가 아닌 것을 전부 버립니다.

**이건 저장 용량을 아끼는 것이지 대역폭을 아끼는 게 아닙니다.** OSV는 생태계당 아카이브 하나를
서버 측 필터링 없이 제공하므로, `db update`는 여전히 슬라이스 1 기준 약 244 MB를 받아서 파싱 후
대부분을 버립니다.

### D16 — 철회된 권고는 수집 시점에 거른다

OSV 레코드에는 철회를 표시하는 선택적 `withdrawn` 타임스탬프가 있습니다. 측정한 Go 덤프에서
8,617건 중 107건(1.2%)이 철회 상태였고, `MAL-*` 4,000건 표본에서는 52건이었습니다. 이를 수집하면
**더 이상 유효하지 않은 권고에 대한 finding**이 생깁니다. 그냥 오탐입니다.

매처가 조회 시점에 건너뛰는 대신 **Provider가 수집 시점에 버립니다.** 그래야 확인을 빠뜨린 코드
경로로 철회된 권고가 새어 나갈 수 없습니다.

### D17 — "unknown"은 일급 심각도 밴드다

**Go 레코드 8,617건 중 4,335건(50.3%)에 `severity` 필드가 아예 없습니다.** 이건 대충 덮을 예외
케이스가 아니라 **데이터의 절반**입니다.

없는 심각도를 `low`나 `none`으로 조용히 바꾸면 **데이터의 공백이 빌드 통과로 바뀝니다.**
`unknown`은 `low < medium < high < critical` 순서의 맨 아래가 아니라 **그 바깥**에 있는 독립
밴드입니다.

여기서 세 가지 동작이 따라 나오며, 세 번째가 존재하는 이유는 앞의 둘로는 부족하기 때문입니다:

1. **unknown finding은 항상 보고됩니다.** 심각도 임계값은 무엇이 빌드를 실패시킬지를 정할 뿐,
   무엇이 출력에 나타날지는 절대 정하지 않습니다.
2. **unknown은 `--fail-on <밴드>` 만으로는 트립하지 않습니다.** 전체 권고의 절반이 미평가인
   상황에서 반대로 하면 모든 스캔에서 발동해 플래그가 무용지물이 됩니다.
3. **`--fail-on-unknown`이 이를 명시적으로 게이팅합니다.** 이게 없으면 (1)과 (2)를 합쳐도 평가되지
   않은 critical 취약점이 여전히 0으로 통과합니다 — 출력에는 찍히지만 통과입니다. 이는 `low`로
   떨어뜨리는 것과 같은 실패이고, 단지 더 시끄러울 뿐입니다. 기본을 켜두면 (2)의 문제를 그대로
   재현하므로 옵트인입니다.

```bash
assay scan img --fail-on high                      # unknown passes; count shown in summary
assay scan img --fail-on high --fail-on-unknown    # unknown also exits 1
```

unknown 개수는 두 출력 경로 모두에 **조건 없이** 들어갑니다. **판단하지 못한 양을 숨기는 임계값은
임계값이 아닙니다.**

심각도가 있는 경우 그것은 CVSS 벡터입니다. Go 덤프에는 `CVSS_V3`(3,688)와 `CVSS_V4`(1,100)가 모두
있으므로 파서는 처음부터 둘 다 처리합니다 — 그리고 D13에 따라 벡터를 저장하고 밴드는 조회 시점에
계산합니다.

**50%라는 수치가 영구적이지 않을 수 있습니다.** CVSS 벡터가 없는 레코드도 NVD가 점수를 매긴 CVE를
alias로 갖는 경우가 흔합니다. NVD 심각도를 보강 소스로 조인하면 — KISA와 같은 메커니즘(D3) —
상당 부분을 채울 수 있습니다. 계획이 아니라 가능성으로 기록해 둡니다.

### D18 — CLI 플래그 이름은 의미가 같은 한 grype를 따른다

`--fail-on`, `--output` 등의 이름을 grype와 공유하는 것은 **의도적**입니다. 플래그 명명은 거의
장르 관례에 가깝고, 마이그레이션하는 사람에게 익숙함이 그대로 이어지며, 주 정확성 검증 수단인
대조 테스트(§5)가 **두 도구가 같은 인자를 받을 때 스크립트로 짜기 쉽습니다.**

여기서 생기는 위험은 공유된 이름 자체가 아니라 **공유된 이름 아래의 다른 동작**입니다. assay가
다른 지점은 발견하도록 방치하지 않고 문서화합니다:

| 플래그 | grype와의 차이 |
|---|---|
| `--fail-on` | 이름도 비교 방식도 같지만 **종료 코드가 다름**: 여기서는 1, grype는 2. grype는 "찾았다"와 "돌릴 수 없었다"를 한 덩어리로 묶지만, D11은 둘을 가르고 assay의 모든 평가 불가 경로가 거기 기대고 있음(D21). |
| `--fail-on <band>` | 밴드 이름이 `none low medium high critical`, grype는 `negligible low medium high critical`. 순서도 자리도 같고, assay는 grype가 만든 이름 대신 CVSS가 0.0에 쓰는 이름을 택함(D21). |
| `--fail-on-unknown` | grype에 대응물 없음. assay의 심각도 순서 바깥에 unknown이 있기 때문에 존재함(D17). |
| `--fail-on-incomplete` | grype에 대응물 없음. 1이 아니라 **2**를 반환함 — 검사되지 않은 패키지는 finding이 아니라 커버리지에 대한 진술이기 때문(D21). |
| 다중 출처 finding의 심각도 | grype는 매치당 밴드 하나를 보고하지만, assay는 모든 출처의 평가를 보고하고 그중 가장 높은 것으로 게이트를 겁니다(D25). Django 3.2.12, finding 19건으로 측정: grype는 assay의 집계와 19/19 일치하고, assay의 GHSA 평가와도 19/19 일치하지만 PYSEC 평가와는 1/15만 일치합니다. 밴드가 같을 때만 일치로 세었으므로, 어긋난 14건은 grype의 실제 밴드와 PYSEC의 `unknown`을 견준 결과입니다. 이 표본에서는 "grype가 가장 높은 것을 취한다"와 "grype가 GHSA를 따른다"를 구분할 수 없습니다. PYSEC가 어느 것에도 평가를 매기지 않기 때문입니다. 둘을 가르려면 GHSA가 아닌 출처가 더 높게 매긴 사례가 필요합니다. |

공유된 이름이 다른 의미를 갖게 될 때마다 이 표에 행을 추가하십시오. **조용히 달라진 플래그가
이름이 다른 플래그보다 나쁩니다.**

### D19 — 레지스트리 접근은 `go-containerregistry`, 레이어 내용은 우리 것

두 번째 서드파티 의존성. 양쪽을 측정한 뒤 의도적으로 채택했습니다.

**직접 짜면 실제로 얼마나 드는가.** Docker Hub 익명 pull은 요청 세 번입니다 —
`WWW-Authenticate` 챌린지를 담은 `401`, 그 챌린지가 지목한 realm에서 토큰 받기, 베어러
헤더를 붙인 매니페스트 재요청 — 그리고 이걸 그대로 하는 stdlib 판은 93줄입니다. 이 숫자
때문에 직접 짜는 게 싸 보였고, 그것이 오해였습니다. 레지스트리 하나, 익명, happy path일
뿐입니다. 세 곳을 재보니 이미 세 갈래로 갈립니다 — Docker Hub는 `auth.docker.io`에서
2,658자 토큰을, GHCR은 자기 호스트에서 52자 토큰을 주고, Quay는 공개 매니페스트에 챌린지
자체가 없습니다. 재시도, 레지스트리의 `Authorization` 헤더를 거부하는 CDN으로의 blob
리다이렉트, 레지스트리별 에러 분류, 그리고 **설정 파일이 아니라 stdio로 대화하는 별도
실행 파일**인 credential helper — 이 전부가 그 93줄에 없습니다.

**채택하면 얼마나 드는가.** 링크되는 모듈 9개, 패키지 46개, 바이너리 6.3 MB → 6.8 MB.
`go.sum`은 47개 늘지만 그중 38개는 의존성의 테스트·툴링 의존성(`cobra`, `blackfriday`,
`opentelemetry`, `testify`)이라 **아무것도 컴파일되지 않습니다.** 이 구분이 중요합니다 —
실행 코드가 아니라 빌드 시점 공급망 표면입니다.

`docker/cli`와 `docker-credential-helpers`는 익명 전용으로 써도 링크됩니다. 즉 프라이빗
레지스트리 자격증명이 나중 작업이 아니라 의존성과 함께 들어옵니다. 이것이 결정적입니다 —
직접 짤 때 비싼 쪽이 자격증명 해석이었는데, 라이브러리를 쓰면 그 절반이 통째로 사라집니다.

**경계.** 의존성이 사주는 것은 레지스트리 프로토콜과 인증뿐입니다. 레이어 순회, whiteout
적용, `/etc/os-release`와 `/lib/apk/db/installed` 파싱은 우리 것으로 남습니다 — 이 프로젝트가
소유하려는 부분이고, 어차피 어떤 라이브러리도 대신 해주지 않습니다.

**레이어 내용은 디스크에 쓰지 않습니다.** 스캔에 필요한 것은 레이어당 파일 두 개뿐이므로
레이어를 스트리밍하며 원하는 항목만 지나가는 길에 읽습니다. path traversal, symlink 탈출,
아카이브 폭탄은 **추출** 취약점입니다. 추출하지 않으면 방어하는 것이 아니라 클래스가
사라집니다.

**Docker 데몬 소스는 제외합니다**(`docs/deferred-decisions.md` 참조). 이것 하나가 링크
모듈을 9 → 27개, 패키지를 46 → 114개로 만듭니다. 그리고 네 소스 중 가장 덜 필요합니다 —
로컬에 이미 있는 이미지는 `docker save`로 넘기면 tarball 소스가 읽습니다.

### D20 — 데이터베이스는 자신이 무엇을 커버하는지 기록한다

`Meta`가 provider들이 받았다고 보고한 생태계 키 집합을 담고, 그 집합에 없는 생태계의 패키지는
**평가하지 않고 skip**합니다.

**막으려는 실패.** 이것이 없으면 매처는 두 상황을 구분하지 못합니다 — 생태계를 수집했고 이
패키지에 권고가 없는 경우와, 생태계를 애초에 수집한 적이 없는 경우. 둘 다 빈 조회로 보입니다.
`Alpine:v3.19`만 담은 데이터베이스에서 같은 패키지를 distro 릴리스만 바꿔 두 번 스캔한 결과:

```
VERSION_ID=3.19.9  ->  finding 1건                                    exit 0
VERSION_ID=3.25.0  ->  "No known vulnerabilities found in 1 package"  exit 0
```

두 번째는 **확신에 찬 오답**이고 가정이 아닙니다. OSV의 Alpine 데이터는 자신이 본 최신
릴리스에서 멈추므로, OSV가 아직 채우기 시작하지 않은 릴리스가 여기 걸립니다.

**Alpine만의 문제가 아닙니다.** Go만 담은 데이터베이스는 PyPI 스캔에도 똑같이 답합니다. 집합은
모든 생태계에 대해 검사하므로 보장이 균일합니다.

**provider가 보고합니다. 양쪽을 다 아는 것은 provider뿐이기 때문입니다.** 뻔해 보이는 두 출처는
둘 다 틀립니다:

- *store가 색인한 것*은 **과잉 주장**합니다. 레코드는 받지 않은 생태계의 affected 항목을
  의도적으로 보존하므로(슬라이스 1의 교차 생태계 수정), `Put`에서 만든 store 쪽 집합은 실제
  데이터베이스에서 `Maven`, `NuGet`, `crates.io` 등 **35개 중 9개**를 받은 적도 없이 커버한다고
  주장했습니다. Maven comparer가 들어오는 날 그 집합은 떠돌이 Maven 키 91개를 가진
  데이터베이스를 보증하고, 모든 Maven 스캔이 clean으로 나옵니다. 처음에 그렇게 썼고 리뷰에서
  잡혔습니다.
- *받은 것*은 **과소 주장**합니다. `db update`는 `Alpine` 아카이브 하나를 받는데 그 레코드가
  `Alpine:v3.2`부터 `Alpine:v3.24`까지를 담으므로, fetch 목록은 아무도 조회하지 않는 키 하나를
  대고 실제 23개를 빠뜨립니다.

provider는 둘 다 압니다 — 어떤 가족을 요청했는지, 그 아래로 어떤 릴리스 키가 돌아왔는지.
`Convert`가 이미 필터에 쓰는 같은 술어로 교집합을 기록하고, `SetMeta`가 provider들이 보고한
것을 합칩니다.

**커버는 존재이지 완전성이 아닙니다.** 이 검사는 "이 생태계를 수집했는가"에 답하지 "그 데이터가
최신인가"에 답하지 않습니다. OSV가 이제 막 채우기 시작한 릴리스는 통과합니다. 그 경계가
맞습니다 — 신선도는 `DataAsOf`의 몫입니다(D12) — 다만 보장은 "이것을 받았다"이지 "이것에 대해
전부 안다"가 아닙니다.

**부분 커버는 기존 종료 코드 의미를 유지합니다.** 아무것도 평가하지 못했으면 이전처럼 2를
반환하고, 일부만 커버되었으면 커버되지 않은 것들이 "Not evaluated"에 개수와 함께 표시되며 종료
코드는 그대로입니다. 미평가가 하나라도 있으면 실패시키는 것은 더 큰 결정이고 — 버전 문자열 하나
파싱 실패로 빌드가 깨집니다 — `--fail-on`과 함께 슬라이스 4에서 다룰 사안입니다.

**스키마 버전 3.** 이 필드는 온디스크 형태의 일부이므로, 그 이전에 만든 데이터베이스는 "아무것도
커버하지 않는다"로 읽히는 대신 안내와 함께 거부됩니다(D5).


### D21 — 판정: 무엇이 빌드를 실패시키고, 종료 코드가 무엇을 뜻하는가

슬라이스 4에서 종료 코드 1이 처음으로 도달 가능해집니다. 무엇이 거기 이르는지를 네 결정이
정합니다.

**`--fail-on <band>`은 1을 반환합니다. 2가 아닙니다.** 같은 이름의 grype 플래그는 2를
반환하여 "취약점을 찾았다"와 "스캔을 돌릴 수 없었다"를 한 덩어리로 만듭니다. 그 둘을 가르는 것이
D11의 존재 이유이고 이 프로젝트 전체가 거기 기대고 있습니다 — 지금까지 만든 모든 "판단할 수
없었다" 경로가 exit 2에 이르는 이유가 정확히 CI가 둘을 구분할 수 있게 하기 위해서입니다. 여기서
grype를 따르는 것은 마이그레이션 메모 한 줄을 아끼려고 그것을 내주는 일입니다. 발산표에
기록합니다(D18).

**`--fail-on-incomplete`는 2를 반환합니다. 1이 아닙니다.** 검사되지 않은 패키지는 finding이
아니라 **스캔이 대상의 얼마를 실제로 덮었는가에 대한 진술**이고, D11은 신뢰할 수 없는 결과에 2를
배정합니다. *아무것도* 평가하지 못했을 때 이미 일어나는 일과도 맞습니다 — 그건 플래그 없이도
오늘 exit 2입니다 — 즉 이 플래그는 두 번째 규칙을 만드는 것이 아니라 기존 규칙을 부분 사례로
확장합니다.

`--fail-on-unknown`과 같은 이유로 opt-in입니다(D17): skip은 일상적입니다. 파싱 불가 버전 문자열
하나, 경계가 망가진 권고 하나, 이 빌드가 지원하지 않는 생태계의 패키지 하나 — 전부 멀쩡한
스캔에서도 skip을 만들고, 기본으로 켜면 계속 울리다가 꺼지게 됩니다.

**밴드는 다섯 개이고 맨 아래가 `none`입니다**: `none < low < medium < high < critical`,
그리고 순서 밖의 `unknown`(D17). CVSS가 0.0을 None으로 명시하고 밴딩은 벡터에서 도출되므로
(D13), 밴드 집합은 도구가 아니라 명세를 따릅니다. grype는 같은 자리를 `negligible`이라
부릅니다. 이름의 발산이고 D18의 표에 기록합니다.

0.0을 `low`로 올리는 것은 D17이 반대 방향으로 금지한 것과 같은 왜곡입니다 — 데이터가 뒷받침하지
않는 심각도를 보고하는 일입니다.

**CVSS v4는 범위에 넣고, 공식이 아닙니다.** 저장된 벡터 27,891개 중 6,531개(23%)가 v4이고 최근
Alpine 권고는 전부 v4이므로, v4를 미루면 **가장 최신 발견들이 `unknown`으로 떨어져**
`--fail-on`의 시야에서 사라집니다. 다만 v4 점수 계산은 옮겨 적기가 아닙니다. 매크로벡터를 찾은
뒤 severity distance, 매크로벡터 depth, 등가 클래스별 proportional distance의 평균으로
보간하며, 권위는 산문이 아니라 참조 구현입니다.

성격이 apk comparer와 같습니다(D9) — 오답이 조용하고 손으로 쓴 테이블은 별로 증명하지 못하는
알고리즘. 신뢰하기 전에 공표된 기대 점수와 상호 검증해야 하고, 그 검증은 커밋 메시지가 아니라
리포지터리 안에 있어야 합니다.

**측정했습니다. D17의 수치가 생태계별이었기 때문입니다.** D17은 전체 권고의 절반이 심각도가
없다고 하는데, 그건 Go 덤프(49.7%)에만 참입니다. 데이터베이스 전체로는 74.9%가 갖고 있고,
생태계별로는 Alpine 98.9%, npm 89.7%, PyPI 75.9%입니다. 즉 **컨테이너 스캔에는 unknown이 거의
없어서** `--fail-on-unknown`은 D17의 서술이 시사하는 것보다 훨씬 덜 시끄럽고, 그만큼 더
쓸모 있습니다.

### D22 — 타깃 분류: 내용으로 판별하되, 사용자가 재정의할 수 있게

`assay scan ./bin/assay`는 존재하는 경로이고, 지금까지 존재하는 경로는 SBOM을 뜻했습니다. CycloneDX
파서에 바이너리를 넘기면 JSON 오류가 나는데, 그러면 읽는 사람이 잘못 읽힌 타깃이 아니라 깨진 문서를
찾으러 갑니다.

**맨경로는 내용으로 분류합니다.** 순서는 고정입니다 — 디렉터리인가, 그다음 `debug/buildinfo`,
그다음 CycloneDX. 각 판별은 쌉니다(buildinfo는 헤더만 읽고 Go 바이너리가 아니면 즉시 실패). 사실
셋은 어떤 실제 입력에서도 동시에 참일 수 없어서 순서가 관측되지 않습니다. 그래도 고정하는 이유는,
네 번째 형식이 추가되는 날 그 배타성이 깨지고 순서 없는 감지는 조용히 동작을 바꾸기 때문입니다.
어디에도 맞지 않는 경로는 셋을 모두 이름 붙인 오류이지, 그중 하나로 조용히 흘러가지 않습니다.

**명시 접두사가 감지를 재정의합니다** — 기존 `docker-archive:`, `oci-dir:` 옆에 `file:`, `dir:`,
`sbom:`. 감지는 휴리스틱이고, 재정의 수단이 없는 휴리스틱은 벽입니다. 인자의 형태도 하나로 유지됩니다.
타깃은 이미 이미지 두 형태에 접두사를 쓰고 있고, "어떤 종류는 접두사, 어떤 종류는 추측"은 "말하지
않으면 추측"보다 설명하기 어렵습니다.

분류기는 자기가 무엇으로 판단했는지 돌려주고 스캔이 그것을 보고하므로, 잘못된 추측은 헷갈리는
오류에서 유추하는 것이 아니라 출력에 그대로 드러납니다.

### D23 — 디렉터리 스캔은 `go.mod`를 읽고, `go`를 호출하지 않는다

"이 프로젝트가 무엇에 의존하는가"에 답이 셋입니다. 이 저장소에서 실제로 잰 값입니다.

| 출처 | 모듈 수 | 무엇인가 |
|---|---|---|
| 바이너리, `debug/buildinfo` | **10** + main | 실제로 링크된 것 |
| `go.mod` require 블록 | **11** | 요구한 것 |
| `go list -m all` | **52** | 모듈 그래프 전체 |

`go list -m all`이 정확한 빌드 리스트이고, 그래서 쓰지 않을 것이 바로 그것입니다. 스캔 시점에 Go
툴체인이 필요하고, 캐시 미스면 네트워크까지 필요합니다. 디렉터리 하나 읽자고 빌드 툴체인을 요구하는
스캐너는 이 도구가 쓰이려는 환경에서 돌지 못하고, D14는 SBOM이나 아카이브 스캔이 네트워크 호출을
전혀 하지 않는다고 약속합니다. *파일시스템* 경로에 툴체인 의존을 더하는 것은 그 약속을 다른 방향에서
깨는 일입니다.

그래서 디렉터리 카탈로거는 표준 라이브러리로 `go.mod`를 직접 파싱합니다. **52개 중 11개**이고, 양쪽
방향으로 틀립니다. 그래프가 이름 붙일 전이 모듈을 놓치고, 바이너리가 링크하지 않는 테스트 전용
모듈을 포함합니다 — `gotest.tools/v3`가 이 저장소의 indirect require에 있고 어떤 빌드 산출물에도
없습니다.

**이것은 감춰진 한계가 아니라 문서화된 한계입니다.** 디렉터리 스캔은 자기가 무엇을 읽었는지 말하고,
빌드된 바이너리가 있으면 그쪽을 스캔하라고 권합니다. 실제로 배포되는 물건의 인벤토리는 그쪽이기
때문입니다. 툴체인 없이 빌드 리스트를 얻으려면 모듈 캐시 위에서 최소 버전 선택을 다시 구현해야 하고,
그건 다른 프로젝트입니다.

### D24 — Go 툴체인은 `stdlib`이라는 이름의 패키지다

실전 데이터베이스에 Go 생태계의 **`stdlib` 권고가 159건** 있고, 평범한 버전 범위를 갖습니다
(`introduced="1.16.0-0"`, `fixed="1.16.1"`). 취약한 툴체인으로 빌드된 바이너리는 취약하고,
`debug/buildinfo`가 툴체인 버전을 알려주므로, 이미 갖고 있는 데이터를 매칭하지 않겠다는 것은 조용한
미탐입니다.

`GoVersion`은 `go1.26.4`로 오고 권고는 `1.26.4`를 쓰므로 접두사는 catalog 시점에 제거합니다. 이
정규화는 하중을 받습니다 — semver comparer가 `go1.26.4`를 아예 거부하는 것을 측정했으므로, 틀리면
틀린 답이 아니라 skip된 패키지가 나오고 그건 최소한 시끄럽습니다. 프리릴리스 형태는 그렇지 않습니다.
`go1.21rc1`과 `go1.26`은 `1.21.0-0`, `1.26.0`과 올바로 정렬되는 무언가로 정규화되어야 하고, 조용한
정렬 버그가 살 곳은 거기입니다.

디렉터리 스캔은 이것을 얻지 못합니다. `go.mod`의 `go` 지시자는 언어 버전 하한이지 빌드할 툴체인이
아니고, 그것을 툴체인으로 취급하면 아무것도 빌드된 적 없는 버전을 보고하게 됩니다.

### D25 — finding은 승자 하나가 아니라 모든 출처의 평가를 담는다

같은 취약점을 두 데이터베이스가 함께 기술하는 일이 흔하고, 서로 다른 말을 합니다. 실제 스캔이
건드리는 패키지들에서 도달 가능한 CVE 그룹 440개를 측정했습니다.

| | |
|---|---|
| 취약점 그룹(CVE 기준) | 440 |
| **레코드가 둘 이상** | **169 (38%)** |
| 그중 레코드 간 심각도가 다름 | 140 |
| 그중 fixed 버전이 다름 | 152 |

불일치는 `GHSA` + `PYSEC`에 몰려 있습니다(169개 중 161개). 실제 데이터베이스의 Django:

```
CVE-2022-28347   GHSA-w24h-v9qh-8gxj -> critical      PYSEC-2022-191 -> unknown
CVE-2018-6188    GHSA-rf4j-j272-fj86 -> high          PYSEC-2018-4   -> unknown
CVE-2016-2048    GHSA-46x4-9jmv-jc8p -> high          PYSEC-2016-14  -> unknown
```

**지금 매처는 먼저 매칭된 레코드를 남기고 나머지를 버리는데**, 그 "먼저"는 누가 정한 것이
아닙니다. 패키지 인덱스는 `ids = append(ids, id)`로 쌓이고 정렬되지 않는 JSON 배열이므로, 순서는
provider가 OSV 아카이브를 훑은 순서 그대로입니다.

현재 데이터베이스에서는 GHSA가 먼저 오고, GHSA가 CVSS 벡터를 갖고 있어서 출력이 맞습니다 —
Django 3.2.12 스캔이 critical 5 / high 10 / medium 4를 보고하고 `--fail-on critical`이 1을
반환합니다. 그건 운입니다. 수집 순서가 뒤집혀 PYSEC가 이기면 같은 critical finding들이
`unknown`으로 보고되고, unknown은 어떤 임계값도 트립하지 않으므로(D17) `--fail-on critical`이
**0**을 반환합니다. critical 취약점 앞에서 CI가 초록이 되는 것 — 슬라이스 4가 없애려고 만들어진
바로 그 결함이, 어디에도 적히지 않고 테스트되지도 않는 세부를 통해 도달 가능합니다.

**2026-08-03 재측정.** 한 번의 스캔이 건드리는 패키지가 아니라 데이터베이스 전체(권고 32,046건,
OSV 데이터 기준일 2026-08-01)와 실제 Django 3.2.12 스캔을 대상으로 다시 측정했습니다.

| | 데이터베이스 전체 | Django 3.2.12 스캔 |
|---|---|---|
| 취약점 그룹(CVE 기준) | 19,715 | finding 19건 |
| 레코드가 둘 이상 | **8,893 (45%)** | **15 (79%)** |
| 그중 심각도 밴드가 다름 | **5,693 (64%)** | **14** |
| …한쪽은 평가가 있고 다른 쪽은 없어서 | 5,423 | 14 |
| …양쪽 다 평가가 있는데 밴드가 갈려서 | 3,530건 중 306 | 0 |
| 그중 fixed 버전이 다름 | 2,210 (25%) | **0** |

심각도 관련 줄은 그대로 성립하고, 그 아래 갈라지는 부분을 읽을 필요가 있습니다. 불일치의 대부분은
한 출처가 평가한 것을 다른 출처가 평가하지 않은 경우(5,423건)이지, 두 출처가 같은 것을 다르게
채점한 경우(306건)가 아닙니다. unknown을 순서 바깥에 두는 D17이 집계를 성립시키는 이유가
그것입니다. 의견 없는 출처가 의견 있는 출처를 어느 방향으로도 이겨서는 안 됩니다.

fixed 버전 비교는 모든 `affected` 항목의 모든 `fixed` 이벤트를 모아 정렬한 집합을 문자열로
견준 것입니다. 한 레코드가 릴리스 브랜치를 나열하고 다른 레코드가 묶어 적으면 과다 계산되고, 두
레코드가 같은 버전을 다르게 적으면(`2.2.28` 대 `2.2.28.0`, `v` 접두사, 에포크) `Comparer`(D9)를
거치지 않으므로 과소 계산됩니다. `last_affected`는 무시하므로 그 방식으로 범위를 닫은 레코드는
수정 버전이 없는 것으로 읽힙니다. 더 엄밀히 정의하려면 매처가 필요해지는데, 그 시점에는 데이터가
아니라 스캔을 재는 것이 됩니다.

**fixed 버전 수치는 재현되지 않습니다.** 최초 측정의 169개 중 152개는 90%인데, 다시 재면
데이터베이스 전체에서 25%이고 `GHSA` + `PYSEC` 조합만 보면 11%(4,488개 중 510개)입니다. 최초
표본이 169개 중 161개를 차지한다고 적은 바로 그 조합입니다. Django의 다중 출처 finding 15건은
fixed 버전이 전부 일치합니다. 최초 수치의 범위는 "실제 스캔이 건드리는 패키지"였는데 그 패키지
목록 없이는 복원할 수 없고, 두 측정이 같은 것을 재고 있지 않을 수도 있습니다. 한 레코드가 다른
레코드에는 없는 릴리스 브랜치의 fixed 경계를 담고 있으면, 정의에 따라 차이로 세어지기도 하고
아니기도 합니다.

D25는 이 수치에 기대고 있지 않습니다. rating이 자기 fixed 버전을 갖는 이유는 출처의 조치 정보가
그 출처에 속하기 때문이며, 출처들이 우연히 일치하든 아니든 메커니즘은 동일합니다. 조용히 계속
쓰지 않고 여기서 바로잡는 이유는, 권위 있게 읽히지만 사실이 아닌 측정치가 이 문서의 KVE 항목이
이미 기록한 것과 같은 종류의 결함이기 때문입니다.

**그래서 finding은 모든 레코드의 평가를 유지합니다.** 승자를 고르지 않으면 순서 의존이 통째로
사라지고, 숨어 있던 불일치가 드러납니다. 설명 가능성을 첫 번째 목표로 삼는 스캐너가 서로 다른 말을
하는 두 권위를 두고 해야 할 일이 그것입니다.

**게이트는 출처들 중 가장 높은 밴드를 씁니다.** 한 레코드 안의 여러 벡터에 `severity.Highest`가
이미 적용하는 규칙을 레코드 사이로 확장한 것입니다. finding은 자신의 가장 나쁜 평가만큼
심각합니다. `unknown`은 이를 희석하지 않습니다. D17이 unknown을 순서의 아래가 아니라 순서 밖에
두므로, 아무 평가도 하지 않은 출처가 critical finding을 통과로 끌어내릴 수 없습니다.

**"출처"는 레코드를 쓴 데이터베이스**이지 그것을 가져온 provider가 아닙니다. 둘은 다릅니다.
`Advisory.Source`는 이미 전부 `osv`이고, OSV가 유일한 provider인 동안 계속 그럴 것입니다. 레코드를
쓴 데이터베이스 — GHSA, PYSEC, GO, ALPINE — 는 오늘 식별자 접두사로 유추할 수밖에 없는데, 접두사는
필드가 아니라 명명 관습입니다. 명시적으로 저장하며, 이는 스키마 변경입니다.

**NVD와 KISA는 여기 없습니다.** assay는 NVD를 수집하지 않으므로 NIST가 무엇으로 평가하는지 말할 수
없고, 그것은 실제 비용이 드는 별도의 수집 결정입니다. KISA는 슬라이스 5가 기록한 이유로 막혀
있습니다. 이 메커니즘은 이미 가진 출처만으로 성립하고 새 출처를 재설계 없이 받아들입니다. 두 이름을
특수 처리하는 대신 이렇게 짓는 이유가 그것입니다.

### D26 — 디렉터리 스캔은 찾은 락파일을 모두 읽고, 읽지 않은 것은 이름을 밝힌다

D23은 디렉터리 스캔이 *Go에 대해* 무엇을 읽는지를 정했습니다. Go만 있지 않은 디렉터리는 정하지
않았고, 그 답은 이 프로젝트가 막으려고 존재하는 바로 그 실패였습니다. `go.mod`,
`package-lock.json`, `requirements.txt`가 함께 있는 디렉터리에서 측정했습니다.

| | 컴포넌트 | finding | 미평가 | 종료 코드 |
|---|---|---|---|---|
| 같은 패키지를 SBOM으로 | 3 | **27** | 0 | 0 |
| `assay scan dir:.` — 이전 | 1 | **3** | **0** | 0 |
| `assay scan dir:.` — 이후, Python 쪽이 `requirements.txt` | 2 | 8 | 0 | 0 |
| `assay scan dir:.` — 이후, Python 쪽이 `poetry.lock` | 3 | **27** | 0 | 0 |

2026-08-03에 스키마 5 데이터베이스(권고 32,106건, OSV 데이터 기준일 2026-08-01)로 같은 픽스처를
다시 측정했습니다. Python 쪽이 락파일이면 디렉터리 스캔이 SBOM과 정확히 일치합니다. `requirements.txt`
이면 일치하지 않고 — Django의 finding 19건이 여전히 보고되지 않습니다 — 다만 스캔이 그 사실을
말합니다.

```
scanned dir:. as a directory
go.mod names 1 module(s); this is what was requested, not what a build links - scan the built binary for that
not read: requirements.txt (not a lockfile: versions may be ranges, not resolved versions)
```

그 줄이 두 번째 절반의 전부입니다. finding 8건짜리 행은 여전히 불완전하지만, 읽는 사람이 그것을
알 수 있는 유일한 형태입니다.

finding 24건이 사라지고, 그러면서 스캔은 `0 not evaluated`를 보고합니다. 이것은 "npm과 PyPI가
미지원"인 상황이 아닙니다. 둘 다 수집되어 있고, 둘 다 comparer가 있고, 다른 모든 경로에서는
정상적으로 매칭됩니다. 디렉터리 cataloger가 아예 보지 않았을 뿐이고, 리포트의 어느 줄도 그 사실을
말하지 않았습니다.

마지막 부분이 이것을 공백이 아니라 결함으로 만듭니다. D20은 평가할 수 없었던 패키지를 개수와 함께
skipped로 보고하게 하여 CI가 "아무것도 못 찾았다"와 "고장 났다"를 구분할 수 있게 합니다. 그런데
읽히지 않은 매니페스트는 패키지를 만들어내지 않으므로 skip 카운터가 셀 대상 자체가 없습니다.
누락을 드러내려고 만든 바로 그 장치에 누락이 보이지 않습니다.

**그래서 디렉터리 cataloger는 락파일을 읽고, 인식했지만 읽지 않은 매니페스트를 모두 밝힙니다.**
두 쪽 다 하중을 받습니다. 읽는 쪽이 누락을 없애고, 밝히는 쪽은 아직 cataloger가 없는 다음 형식이
같은 방식으로 조용해지는 것을 막습니다. 후자가 미지원 형식과의 접촉에서 살아남는 부분입니다.

**락파일만** — `package-lock.json`과 `poetry.lock`. 둘 다 해석된 정확한 버전을 담으므로 `go.mod`와
달리 D23의 "요구 대 링크" 간극을 물려받지 않습니다. 락파일은 설치되는 것 **그 자체**입니다.
`requirements.txt`는 인식하되 읽지 않은 것으로 이름을 밝힙니다. 락파일이 아니고 — `Django>=3.2`는
버전이 아니라 제약입니다 — 범위를 권고의 범위에 맞추는 것은 버전을 맞추는 것과 다른 문제이며,
고정되지 않은 것에 대해 조용히 "취약하지 않음"이라고 답하게 됩니다. 그것은 미탐이므로 여기 끼워
넣지 않고 별도 결정을 기다립니다.

**루트만이 아니라 제한된 하위 탐색.** 매니페스트는 하위 디렉터리에 있습니다 — `frontend/`,
`services/api/`. 루트만 읽으면 지극히 평범한 저장소 구조에서 이 결함을 한 단계 아래에 그대로
재현하게 됩니다. 탐색은 `node_modules`, `vendor`, `.git`을 건너뜁니다. 의존성 트리 안의 락파일은
이 프로젝트가 아니라 그 의존성 자신의 요구를 기술하기 때문입니다. 깊이도 제한하여 디렉터리 중첩만으로
스캔을 무한정 느리게 만들 수 없게 합니다. 두 제한 모두 D23의 방식대로 출력에 밝힙니다.

**밝힐 때는 개수가 아니라 파일 이름을 말합니다.** "읽지 않은 매니페스트 1건"은 뭔가 빠졌다는 것만
알려줄 뿐 무엇을 해야 할지 알려주지 않습니다. `requirements.txt (not read: not a lockfile)`는 어느
트리가 평가되지 않았고 왜 그런지를 알려줍니다. 설명 가능성이 첫 번째 목표이고, 그것은 검사한 것만큼
검사하지 *않은* 것에도 적용됩니다.

### D27 — NVD는 평가 출처이고, CVE로 조인하며, 결코 매칭 소스가 아니다

assay가 `unknown`이라고 말하는 것의 절반은 모두에게 unknown인 것이 아닙니다. 2026-08-03에 실제
데이터베이스와 NVD 2.0 API로 측정한 결과, 점수 낼 벡터가 없는 권고 8,029건 중 60건 무작위 표본에서
NVD가 **93%**에 점수를 매겼고 **48%를 high 이상**으로 평가했습니다. assay 자기 바이너리 스캔이 그
대가를 보여줍니다. finding 3건이 전부 무평가라 존재하는 가장 낮은 임계값인 `--fail-on low`조차 0을
반환하는데, NVD는 그중 둘을 7.8과 5.3으로 매깁니다.

**조인 키는 CPE가 아니라 CVE입니다.** NVD는 매치 데이터를 `vendor:product`로 키잡는데, 언어
패키지의 경우 그 쌍은 어떤 purl로도 유도할 수 없는 큐레이션된 문자열입니다.
`pkg:golang/gopkg.in/yaml.v3`는 `cpe:2.3:a:yaml_project:yaml`이고, `django`는 벤더가 둘로 갈립니다.
OSV와 NVD를 공유 CVE로 조인해 사전을 배울 수도 있지만, 50건을 표본으로 재보면 신뢰할 매핑을
가르치는 비율이 Alpine 85%, PyPI 71%, npm 50%, **Go 11%**입니다. 그리고 무평가 권고 8,029건 중
4,125건이 Go입니다. CPE 없는 레코드는 NVD가 보강하지 않기로 한 `Deferred` 상태이므로 기다려도
달라지지 않습니다. 자세한 내용은 `docs/deferred-decisions.md`에 있습니다.

그래서 NVD는 여기서 딱 한 질문에만 답합니다. *NIST는 이 CVE를 몇 점으로 보는가?* 패키지가
영향받는지는 결코 판단하지 않습니다. 그것은 OSV와 생태계별 `Comparer`(D9)의 몫이고, 이것이 두 번째
매처가 아니라 작은 provider인 이유입니다.

**Rating이므로 D25가 이미 처리 방식을 정해두었습니다.** NVD 점수는 `Database: "NVD"`로
`Finding.Ratings`에 들어가고, 판정은 rating들 중 가장 높은 밴드를 취하며, `unknown`은 여전히 순서
바깥에 있습니다(D17). **판정이 바뀝니다.** 그것은 부작용이 아니라 목적입니다. 모든 OSV 출처가
평가하지 않은 finding이 이제 `--fail-on high`에 도달할 수 있습니다. 종료 코드 계약은 그대로이고,
달라진 것은 집계할 것이 늘었다는 점뿐입니다.

**다만 NVD 평가는 결코 표시되는 레코드가 되지 않습니다.** D25는 finding이 자기 밴드를 정한 레코드를
보여준다고 정했습니다. NVD는 밴드를 정하지만 finding을 설명 가능하게 만드는 것을 주지 않습니다.
우리가 비교한 범위도, `Evidence`도, 수정 버전도 없습니다. 매칭은 OSV로 했고 NIST에는 점수만
물었습니다. 그것을 표시하면 뒤에 아무것도 없는 권고를 화면에 올리는 것이고, 목표 #1에 반합니다.
그래서 D25의 규칙이 한 단어만큼 좁아집니다. finding은 자기 밴드를 정한 **매칭된** 레코드를 보여주고,
NVD 평가는 표시되지 않은 채로 집계를 올릴 수 있습니다. `--explain`의 출처별 내역에는 나오며, 읽는
사람이 바로 그것을 찾는 자리가 거기입니다.

**`db update`가 가져오고, 스캔은 절대 가져오지 않습니다**(D14). ~~전체 동기화는 187 요청이고
키 없는 제한에서 약 20분입니다.~~ **그 추정은 틀렸고, 실제 실행이 그것을 찾아냈습니다.**

레이트 리밋 대기 시간만 센 값이었습니다. 2026-08-03 측정, 2,000건 페이지 하나:

| | |
|---|---|
| 비압축 | 4.3 MB, **114.5초** |
| gzip | 532 KB, **135.8초** |
| 500건, gzip | 178 KB, 41.6초 |

압축은 바이트를 8배 줄이지만 시간은 줄이지 않고, 비용이 레코드당 거의 선형입니다. 즉 **NVD는 파일을
서빙하는 것이 아니라 응답을 생성하며, 페이지 크기는 총 시간을 바꾸지 않습니다.** 따라서 372,628건은
약 **7시간**이고, 187번의 레이트 리밋 대기는 그중 20분입니다. 앞서 한 번 나온 33초는 이상치였고, 틀린
수치는 거기서 나왔습니다.

결과가 둘, 둘 다 실재합니다.

- HTTP 클라이언트 타임아웃이 2분이었습니다. 실제 동기화가 첫 페이지에서 죽었습니다. 135.8초에 2분은
  여유가 아닙니다. 지금은 10분이고, 추측이 아니라 측정값입니다.
- **사용자당 7시간은 누구도 유지하지 않는 데이터베이스입니다.** 그래서 NVD는 **옵트인**이고
  (`NVD_ENABLE`), `Options.Since`가 `lastModStartDate`로 실행 범위를 제한합니다
  (`NVD_SINCE_DAYS`, API의 120일 창으로 상한).

  ~~빌더가 전체 한 번, 이후 매일 델타를 돕니다.~~ **그럴 수 없고, 머지 전 리뷰가 이 문장이 문서뿐
  아니라 코드에서도 틀렸음을 잡아냈습니다.** `db update`는 새 데이터베이스에 빌드한 뒤 live 위로
  rename하므로 이전 패스를 이어받는 것이 없습니다. 즉 범위를 제한한 실행의 창이 그 데이터베이스의
  *전체* NVD 커버리지입니다. 적힌 대로 — 전체 한 번, 이후 매일 `NVD_SINCE_DAYS=1` — 따라 하면
  372,000건이던 자리에 ~300건이 남고, 어제 수정되지 않은 CVE를 가진 모든 finding이 이유도 없이
  `unknown`으로 되돌아갑니다.

  진짜 델타는 빌더가 기존 데이터베이스 위에 쌓아야 하고, 그것은 배포 슬라이스의 몫입니다. 그때까지는
  창을 없는 척하는 대신 **공개합니다.** `Provenance.Window`가 실제로 무엇을 커버했는지 기록하고
  `db status`가 `COVERED`로 출력합니다. 그러지 않으면 NVD 하루치를 가진 데이터베이스가 전부를 가진
  것과 구분되지 않기 때문입니다(D20).

### 첫 실제 부트스트랩의 비용, 2026-08-04

데이터베이스를 배포하려면 실제로 하나를 만들어야 했고, 다섯 번 만에 됐습니다. 네 번의 실패가 각각
다른 결함이었고, 어느 것도 코드를 읽어서는 보이지 않았습니다.

| 시도 | 실패 시점 | 증상 | 결함 |
|---|---|---|---|
| 1 | 2분 51초 | `404` | 창이 120일 **+ OSV 페치 시간** |
| 2 | 42분 | `503` | 재시도가 아예 없음 |
| 3 | 116분 | `stream error: INTERNAL_ERROR` | 재시도가 HTTP 상태만 매칭 |
| 4 | 5시간 52분 | `startIndex=246000`에서 `503` | 재시도 예산 62초, 알림은 `io.Discard`로 |
| 5 | **27분 26초, 성공** | — | 30일 창, **rating 23,433건** |

남길 만한 것 넷:

**`NVD_SINCE_DAYS=120`은 의미 있는 축소가 아닙니다.** 4차 시도가 37만 2,628건 코퍼스에서
`startIndex=246000`까지 갔습니다. NVD가 재채점·참조 추가로 레코드를 계속 건드리기 때문에, 120일치
*수정분*이 사실상 피드의 대부분입니다. 창은 훨씬 짧을 때만 작업을 줄입니다 — 30일은 27분이고, 이건
측정값입니다.

**문서상의 최대값을 쓸 수 없었습니다.** NVD는 `lastModStartDate`/`lastModEndDate` 범위를 요청
시점에 검사합니다. `Since`는 옵션을 읽을 때, 끝은 동기화가 시작할 때 계산되는데 그 사이에
`db update`가 모든 권고 provider를 돌립니다. 그래서 `NVD_SINCE_DAYS=120`이 120일 + 몇 분으로
도착했고 404를 받았습니다. 지금은 양쪽 끝이 확정되는 요청 시점에 clamp합니다.

**재시도 예산은 포기했을 때 잃는 것에 맞춰 재야 합니다.** 첫 스케줄은 총 62초였고, 4차 시도는
5시간 52분을 쌓아놓고 일시적 장애 하나에 전부 버렸습니다. 그 스케줄의 모든 값이 0이 아니었으니,
"각 대기가 실제 대기다"는 애초에 지킬 성질이 아니었습니다 — 예산이 성질입니다. 지금은 약 12분이고,
매일 도는 워크플로의 60분 타임아웃 안에는 여전히 들어갑니다.

**일시적 실패를 열거하면 이미 본 것만 덮습니다.** 첫 재시도는 방금 503을 봤다는 이유로 HTTP 상태만
매칭했고, 3차 시도는 본문 디코드 중에 드러난 HTTP/2 전송 오류로 죽었으며 재시도는 발동조차 안
했습니다. 지금은 deny-list입니다. 컨텍스트 취소와 429 아닌 4xx만 빼고 전부 재시도합니다.

부끄러워할 만한 것은 관측 쪽 실패입니다. `Options.Progress`는 존재했고 바로 이 문제의 답이라고
문서화까지 되어 있었는데 writer에 연결된 적이 없어서, 4차 시도가 재시도 4번을 하고도 "retries
fired: 0"이라고 기록했습니다. 그리고 `annotating with NVD…`와 결과 사이에 아무것도 출력되지 않아서,
동작 중인 동기화와 멈춘 것을 구별하는 유일한 방법이 프로세스 밖에서 임시 데이터베이스가 커지는지
보는 것이었습니다. 둘 다 고쳤고, 둘 다 테스트가 찾아낸 것이 아닙니다.

남은 공백은 구조적이고 고치지 않았습니다. **실패한 동기화는 전부를 잃습니다.** `Update`는 임시
데이터베이스에 빌드하고 마지막에만 설치하므로, 2·3·4차 시도가 각각 42분·116분·352분의 완료된
작업을 버렸습니다. 재시도는 페이지 하나를 살릴 뿐 실행을 재개 가능하게 만들지 않습니다. 그것을
가능하게 하는 것은 체크포인트이고, 만들지 않았습니다.

더 근본적인 답은 전체 동기화가 애초에 모든 사용자의 문제가 아니어야 한다는 것입니다. 그것이
`docs/deferred-decisions.md`의 *데이터베이스를 OCI 아티팩트로 배포* 항목이고, 그 재검토 조건인
"CI 재빌드 시간이 병목이 될 때"를 이 측정이 발동시켰습니다. grype와 trivy 모두 그렇게 동작합니다.
빌더가 만들고, 나머지는 받습니다.

레코드의 98%가 점수를 갖고 있습니다. API 키는 레이트 리밋을 열 배로 올려주며 지원하되 필수는
아닙니다. 병목이 페이싱이 아니라 NVD의 응답 생성이므로 7시간을 바꾸지는 못합니다.

**실제 피드로 측정, 2026-08-03.** 범위를 제한한 동기화(`NVD_SINCE_DAYS=30`, 최근 30일 내 수정된
CVE)로 **rating 21,460건**을 받았고, 문제의 finding들이 최근 것이라 주장을 확정하기에 충분합니다.

`assay scan ./bin/assay`, 전후 비교:

| | 이전 | 이후 |
|---|---|---|
| finding | 3 | 3 |
| 무평가 | **3** | **1** |
| `--fail-on low` | 0 | **1** |
| `--fail-on high` | **0** | **1** |
| `--fail-on critical` | 0 | 0 |

이후의 finding 3건:

```
stdlib                          high     GO-2026-4970 unknown + NVD CVE-2026-39822 high (7.8)
stdlib                          medium   GO-2026-5856 unknown + NVD CVE-2026-42505 medium (5.3)
github.com/klauspost/compress   unknown  GO-2026-5841 - CVE가 없어 어떤 조인도 닿지 않음
```

세 번째 행이 finding 3건짜리 스캔에 나타난 13%이며, 이 결정이 그렇게 될 것이라고 적은 그대로입니다.
여전히 `unknown`이고, 여전히 요약에 세어지고, 여전히 혼자서는 어떤 임계값도 트립하지 않습니다(D17).

`--explain`이 좁히기가 작동함을 보여줍니다.

```
severity: high (7.8)   [highest of 2 sources]
  GO     GO-2026-4970    unknown          fixed 1.26.5
  NVD    CVE-2026-39822  high (7.8)       fixed -  https://nvd.nist.gov/vuln/detail/CVE-2026-39822
```

밴드는 NVD에서 왔지만, 표시되는 권고와 매칭된 범위와 수정 버전은 전부 assay가 실제로 비교한
레코드에서 옵니다. NVD의 `fixed`가 비어 있는 것은 NIST가 이 패키지에 대한 조치를 발표하지 않았기
때문이고, 리포트는 남의 것을 빌려오는 대신 그렇게 말합니다.

**커버리지는 건드리지 않습니다**(D20). NVD는 생태계가 아니며, NVD 점수가 있다고 해서 `Covers()`가
생태계를 보고해서는 안 됩니다. 그러면 이 데이터베이스가 수집한 적 없는 생태계의 패키지가 미평가로
보고되지 않게 되고, 그것이 D20이 막으려고 존재하는 바로 그 실패입니다.

**13%는 남습니다.** 무평가 권고 8,029건 중 1,008건은 CVE가 아예 없어서 어떤 설계로도 조인이 닿지
않습니다. 나중에 메울 공백이 아니라 이 결정의 정직한 상한이며, 위 바이너리 스캔의 finding 3건 중
하나로 실제로 나타났습니다.

### D28 — 데이터베이스는 중앙에서 빌드되어 OCI 아티팩트로 배포된다

한 머신이 일정에 따라 데이터베이스를 빌드해 `ghcr.io/kun9497/assay-db`에 배포하고, 나머지는 모두
`assay db update`로 그것을 받아옵니다. `assay db build`는 여전히 존재하고 여전히 업스트림
provider들로부터 빌드하지만, 이제는 배포자의 명령이지 일반 사용자의 기본 경로가 아닙니다.
아티팩트의 태그는 스키마 버전입니다(`Ref`가 `:v7`로 렌더링). 그래서 바이너리는 항상 자신이 읽을 수
있는 아티팩트만 요청합니다. 스키마가 올라가면 옛 태그에 대해서는 깔끔한 "찾을 수 없음"이 나올 뿐,
잘못 해석할 데이터베이스를 받는 일은 없습니다. `store.DefaultPath`가 온디스크 레이아웃에 이미 주는
것과 같은 보장입니다(D5). 아티팩트의 `DataAsOf`는 구성 요소들 중 **가장 오래된** 것을 따르며 가장 최신 것을 따르지
않습니다(`dbcmd.Push`의 `oldestDataAsOf`는 `Meta.Providers`와 `Meta.Ratings`를 함께 하나의
최솟값으로 접습니다 — `--seed` 빌드는 `Providers`는 건드리지 않고 `Ratings`만 이어받으므로,
advisory는 방금 다시 빌드했지만 rating은 석 달 전 것인 데이터베이스는 advisory의 최신성이 아니라
rating의 오래됨을 게시해야 합니다). "한 구성 요소가 낡으면 전체가 낡은 것"이라는 D12의 규칙을
데이터베이스 하나의 메타데이터 안에 이미 적용하던 것을, 배포되는 것 자체에 찍히는 값으로 확장한
것입니다. **스캔은 여전히 아무것도 가져오지 않습니다**(D14). 데이터베이스 쪽에서 네트워크를
건드리는 명령은 `db update`, `db build`, `db push` 셋뿐이고, 스캔은 디스크에 이미 있는 것만
읽습니다.

**왜 지금이어야 했는가.** D27은 전체 NVD 패스가 약 **7시간**임을 측정했습니다. NVD는 페이지 크기나
압축과 무관하게 2,000건 페이지 하나를 만드는 데 114–136초가 걸리므로, 비용은 API의 응답 생성
자체이지 클라이언트가 조정할 수 있는 것이 아닙니다. GitHub Actions는 잡 하나에 **6시간** 상한을
둡니다. 예약 워크플로는 이 결정이 요구하는 빌드를 실행할 수 없고, 마지막으로 배포된 아티팩트에서
시작해(seed) 범위를 제한한 창(`NVD_SINCE_DAYS`)만 위에 쌓을 수 있을 뿐입니다. 그것이 바로 슬라이스
8의 seeding이 존재하는 이유입니다. seeding 없이 배포만 하면 절대 자신이 배포하는 아티팩트를 채울 수
없는 파이프라인을 내놓는 셈입니다. 7시간짜리 전체 패스 한 번은 로컬에서 사람이 손으로 하는
부트스트랩이 됩니다. 한 번 빌드하고 한 번 push하면, 그 뒤 모든 예약 실행은 push된 것에서 seed
합니다.

**스키마가 올라가면 배포된 아티팩트는 무효가 되고, 부트스트랩을 다시 해야 합니다.** 태그가 곧
스키마 버전이므로, `store.SchemaVersion`을 올리는 것은 배포된 것을 마이그레이션하지 않습니다 —
모든 클라이언트가 요청하는 대상의 이름을 바꿀 뿐입니다. 스키마 상향이 merge되는 순간부터 `db ref`는
`:vN+1`을 출력하고, 누군가 `:vN+1` 아티팩트를 빌드해 push하기 전까지 `db update`는 깔끔한 404를
받으며, 예약 워크플로의 seed 단계도 같은 태그를 읽으므로 함께 실패합니다. 실패가 요란한 것은 애초에
스키마로 태그를 붙이는 목적 그 자체입니다 — 그 대안은 바이너리가 잘못 읽을 데이터베이스이니까요.
하지만 이것은 저절로 낫지 않고, 예약 빌드가 고쳐줄 수도 없습니다. 그 잡은 seed 위에 제한된 창을
쌓는 일만 할 수 있는데, 쌓을 `:vN+1` seed가 아직 없기 때문입니다. 그러므로 이 결정이 최초
부트스트랩으로 설명하는 로컬 전체 빌드 한 번과 push 한 번은 **스키마가 올라갈 때마다**, merge 직후에
다시 해야 합니다 — 일회성 셋업 단계가 아니라 릴리스 단계입니다. KISA 보강 브랜치가 그 실례입니다.
`:v6`만 배포된 상태에서 스키마를 v7로 올리므로, 그대로 merge하면 v7 아티팩트를 push할 때까지
`db update`와 일일 워크플로가 망가진 채로 남습니다.

**왜 `ghcr.io`이고, 왜 새 비용이 들지 않는가.** `go-containerregistry`는 이미 직접 의존성입니다.
registry `Source`(슬라이스 2b)가 이미지를 받기 위해 이미 인증, 매니페스트 처리, blob 전송을 하고
있습니다. 같은 라이브러리로 데이터베이스를 OCI 아티팩트로 배포하는 것은 새 의존성도 새 프로토콜도
더하지 않습니다. `remote.Write`/`remote.Image`와 `authn.DefaultKeychain`을 두 번째 종류의
콘텐츠에 재사용할 뿐입니다. 이는 grype와 trivy가 이미 쓰는 형태이기도 합니다. 빌더가 만들고
나머지는 받는 구조이므로, 독자적인 배포 형식을 새로 고안하는 대신 검증된 패턴을 빌려온 것입니다.

**왜 seed는 rating만 옮기고 advisory는 옮기지 않는가.** `dbcmd.Update`의 seeding 단계는 provider
루프가 돌기 전에 seed 데이터베이스의 모든 `Rating`을 복사하지만(`Store.EachRating`), advisory는
seed 여부와 무관하게 매번 provider들로부터 다시 빌드됩니다. advisory까지 함께 옮기는 대안은
업스트림이 나중에 `withdrawn`으로 표시하는 advisory가 seed된 데이터베이스에서 결코 제거되지
못한다는 뜻이 됩니다. seed 단계 이후로는 아무도 그것을 다시 들여다보지 않기 때문입니다. D16이
철회된 advisory를 굳이 ingestion 단계에서 걸러내는 이유가 바로 어떤 코드 경로도 그 확인을 잊을 수
없게 하려는 것인데, ingestion을 건너뛰는 seed는 정확히 그렇게 잊힌 경로가 됩니다. rating에는 그런
위험이 없습니다. `PutRating`은 키로 덮어쓰므로, 이번 실행의 provider도 평가한 CVE에 대한 낡은 seed
rating은 그대로 교체되고, 이번 실행의 provider가 건드리지 않은 것(이번 주기에 돌지 않은
annotator)은 `unknown` 대신 마지막으로 실제 있던 값을 계속 보여줍니다. `db status`의 `COVERED`
컬럼이 바로 그것을 위한 것입니다(D20, D27).

### D29 — 보강은 로컬에서만 만들고, `db push`는 배포 전에 그것을 벗겨낸다

`KISA_ENABLE=1`이 설정되면 `db build`가 KISA 보안공지로 `enrichment` 버킷을 채웁니다.
`db push`는 데이터베이스의 스테이징된 복사본에서 그 버킷을 비운 다음, 그 복사본의 **라이브 데이터를
밖으로 복사해** 새 파일을 만들고 그것을 패킹합니다. 그래서 배포되는 바이트는 애초에 그 레코드를 담은
적이 없습니다. `db update`는 KISA의 한국어 텍스트를 결코 전달하지 않습니다 — 원하는 사람은 직접
로컬에서 `db build`를 돌려야 합니다.

**왜.** KISA 사이트 푸터는 `Copyright(C) 2026 KISA. All rights reserved.`이고 공공누리(KOGL)
표시가 없습니다(위 *약관* 항목에 기록). 이는 데이터를 **재배포**하는 것을 제한하지, 그것으로
**스캔**하는 것을 제한하지 않습니다 — 받아온 바로 그 머신에서 빌드하고 읽는 데이터베이스는
재배포가 아닙니다. `db push`는 재배포입니다. 공개 레지스트리인 `ghcr.io/kun9497/assay-db`에
게시하니까요. 그래서 보강은 그것을 빌드한 머신에만 남고, 그 로컬 사본만이 그것을 담습니다.

**재검토 트리거는 라이선스 문제가 풀리는 것입니다** — 사이트에 공공누리 표시가 붙거나, KISA가
재배포를 허용한다고 직접 답하는 경우입니다. 그렇게 되면 D29를 뒤집는 것은 `push.go`의
`stripEnrichment(staged)` 호출을 지우는 것이지 — 뒤따르는 compaction은 그 시점에 살아 있는 것을
그대로 복사하므로, 벗겨내기가 사라지면 레코드는 그냥 함께 넘어옵니다 — 보강이 어디 사는지를
재구성하는 일이 아닙니다. 다른 모든 것과 같은 bbolt 데이터베이스에, rating과 똑같이 `(CVE, Source)`로 키를 잡아
넣어둔 것이 바로 그 되돌리기를 그만큼 작게 만들려는 의도였습니다. KISA 데이터를 위한 별도 파일이나
별도 아티팩트도 같은 이유로 검토했다가 미뤘습니다(`docs/deferred-decisions.md`의 *KISA 데이터를
별도 아티팩트로 분리* 참조) — 그 모양은 라이선스가 풀려야만 값어치를 하고, 지금 만들어 두면 끝내
풀리지 않을 경우 나중에 도로 허물어야 합니다.

**보강 실패는 경고할 뿐, 빌드를 실패시키지 않습니다.** `Provider`나 `Annotator`의 실패는 `db
build`를 그대로 중단시킵니다 — 닿지 않는 OSV 미러나 깨진 NVD 동기화가 부분적인 데이터베이스를
조용히 내놓아서는 안 되기 때문입니다. 반면 닿지 않는 KISA 엔드포인트는 독자가 한국어 산문 조금을
잃는 것 말고는 아무 대가가 없습니다 — 보강은 판정을 바꿀 수 없으므로(D3), 그것 때문에
데이터베이스를 통째로 보류할 정확성상의 이유가 없습니다.

**리뷰 중에, 테스트가 아니라 리뷰로, 벗겨내지 않은 데이터를 배포하는 서로 다른 경로 여섯 개가
발견됐습니다.** 각각 이제 하나씩 잡혀 있습니다.

1. 벗겨내는 호출 자체를 지운다.
2. 실제로 패킹되는 스테이징된 복사본이 아니라 라이브 데이터베이스를 벗겨낸다 — 두 쪽 다
   터집니다. 아티팩트는 산문을 그대로 담고, 빌더는 자기 사본을 잃습니다.
3. 벗겨내기 실패를 `return 2`에서 경고로 낮춰서, 벗겨내지 못해도 push가 그대로 끝나게 한다.
4. 항상 벗겨내는 대신 `Meta.Enrichment`가 비어 있지 않을 때만 벗겨내도록 조건을 건다 — 버킷에는
   레코드가 있는데 아무것도 출처를 기록하지 않은 경우 그대로 뚫립니다.
5. `--force`가 벗겨내기 실패를 무시하게 한다. `db push`의 다른 거부(배포 커버리지를 좁히는 것)를
   이미 무시할 수 있는 것과 같은 모양입니다. 그러나 두 가드는 서로 다른 것을 지킵니다. 커버리지
   가드는 데이터베이스가 좁아지는 것을 막고, 그것은 정말 원하는 배포자가 재정의할 수 있는
   선택입니다. 라이선스 가드는 아예 재배포할 수 없는 데이터를 지키고, 그것은 누구도 재정의할 수
   없습니다.
6. **데이터가 아니라 버킷을 지운다.** 위의 가드는 전부 지켜졌는데도 — 벗겨내기는 스테이징된
   복사본에 대해 조건 없이 돌았고, 그 실패는 치명적이었습니다 — 배포된 아티팩트는 여전히 KISA의
   산문을 담고 있었습니다. bbolt의 `DeleteBucket`은 그 레코드가 있던 페이지를 **해제(free)** 할
   뿐 0으로 덮지 않고, `dbartifact.Pack`은 해제된 페이지까지 포함해 파일 전체를 읽어 gzip합니다.
   이 브랜치에서 측정한 값: 보강 레코드 200건짜리 데이터베이스를 제자리에서 벗겨내도 131,072바이트
   결과물 안에 그 텍스트가 **546번** 남았습니다 — 배포된 레이어에 `gunzip`을 걸고 `strings`를
   돌리면 한국어가 그대로 복원됩니다. 해법은 제자리 삭제를 그만두는 것입니다. 벗겨낸 뒤
   `store.CompactInto`가 스테이징된 복사본의 **라이브** 데이터를 새 파일로 복사하고(`bolt.Compact`,
   이미 직접 의존성), 해제된 페이지는 라이브 페이지가 아닙니다. 순서가 핵심입니다 — 먼저
   compaction하면 레코드가 라이브 데이터인 채로 그대로 복사됩니다.

경로 6은 1–5와 종류가 다르고, 테스트에 대해 말해 주는 것도 다릅니다. 앞의 다섯은 그 호출을 **비켜
가는** 분기이고, 여섯 번째는 그 호출이 자기 이름대로 하지 않은 것입니다.
`TestPush_NeverPublishesEnrichment`는 이것을 볼 수 없었습니다. 아티팩트를 받아 `EnrichmentFor`,
`EachEnrichment`, `Meta`에 묻는데, 그것은 데이터가 살아남는 자리보다 한 층 **위**이고, 레코드가 그
아래 파일 안에 그대로 있는 동안 셋 다 정확히 "없음"이라고 답하기 때문입니다. 이것을 잡는 단언은
**압축을 푼 레이어 바이트**에서 픽스처 자신의 텍스트를 훑습니다. `gunzip | strings`가 보는 것과 같은
시야이고, 그 안의 어떤 단언도 버킷 API를 다시 거치지 않습니다. 제자리 삭제 방식으로 되돌리면 그
단언은 빨개지고 버킷 수준 테스트는 전부 초록으로 남습니다 — 그 짝이야말로 이것을 문서가 아니라
커버리지로 만들어 주는 것입니다.

기록된 판단은, 스테이징된 복사본을 조건 없이 벗겨내고 패킹할 파일을 라이브 데이터만으로 다시 만들며
둘 다 실패 시 치명적이고 어떤 플래그로도 우회할 수 없는 지금 모양이 merge해도 안전하다는 것입니다.
이 문단의 이전 판은, 여섯 번째 경로가 나오면 그것은 `Push`의 분기가 아니라 `Push` 자체의 모양이
문제라는 뜻이고 가드를 하나 더 붙이는 대신 구조를 다시 짜야 한다는 신호라고 적었습니다. 실제로 그런
일이 일어났고, 그렇게 처리했습니다. 이 수정은 배포용 파일을 **만드는 방식**을 바꿨을 뿐 여섯 번째
분기를 더하지 않았습니다. **일곱 번째** 경로가 나온다면 같은 질문을 다시 던지게 되고, 그때의 답은
보강이 배포되는 데이터와 파일을 아예 함께 쓰면 안 된다는 쪽일 가능성이 큽니다
(`docs/deferred-decisions.md`의 *KISA 데이터를 별도 아티팩트로 분리* 참조).

### D30 — `affected[].versions`의 읽을 수 없는 항목은 건너뛰고 세지, 치명적이지 않다

`AffectsVersion`은 advisory의 범위를 먼저 걷고, 열거된 `versions[]` 목록으로 넘어갑니다. 그
목록에서 비교가 실패하면 advisory 전체가 함께 실패했습니다. 두 피연산자는 정반대의 뜻인데 코드가
그것을 뭉뚱그렸습니다.

- **설치된 버전**은 왼쪽 피연산자이고 루프 내내 고정이므로, 읽을 수 없으면 정말로 모든 항목이
  실패합니다. 여기서 건너뛰면 전면적 실패가 조용한 clean 판정으로 바뀝니다. 루프 앞에서 한 번
  검사하고, 여전히 중단합니다.
- **열거된 버전**은 오른쪽 피연산자이고 상류 데이터입니다. v7 데이터베이스로 측정하니 열거 항목
  1,309,665개 중 2,411개(0.184%)가 파싱되지 않고, affected 항목 154건을 오염시킵니다. 그중 하나면
  자기 버전은 멀쩡히 읽히는 패키지가 그 advisory에 대해 평가 불가로 보고되기에 충분했습니다.

파싱되지 않는 열거 버전은 파싱되는 버전과 같다고 보일 수 없으므로, 그것을 건너뛴다고 해서 중단이
내렸을 결론을 잃지 않습니다 — 목록의 나머지가 함께 버려지는 것만 막을 뿐입니다. `AffectsVersion`은
읽지 못한 항목을 돌려주고, matcher는 하드 실패와 똑같이 그 advisory에 `Skipped`를 기록합니다.
**그 기록이 안전성 논거의 전부입니다.** 이제 판정이 읽지 못한 데이터 위에서 내려지므로, 기록이
없으면 시끄러운 놓침이 조용한 놓침이 됩니다. "영향 없음" 경로에서도 발동합니다. 읽지 못한 항목
위에서 계산된 clean 답은 affected 답과 똑같이 불완전하기 때문입니다.

**이것이 대체하는 주석은 정반대를 단언하고 있었고, 그래서 리뷰를 통과했습니다.** 그 주석은
advisory를 실패시키는 근거로 "실패는 설치된 버전에서 올 수밖에 없다"를 들었는데, 그 경우는 지금도
중단하는 바로 그 경우입니다. 직접 재현했습니다 — 설치 `3.0.0`, 목록
`["1.0.0", "0.9-stable", "2.0.0"]`, 그리고 패키지는 자기가 아닌 항목 때문에 평가 불가로 돌아옵니다.

**정직하게 잰 크기.** 오염된 154건 중 **2건**이 판정을 바꾸고, 나머지 152건은 계산된 판정을 얻되
불완전 표시를 그대로 유지합니다. 그 2건의 값어치는 구체적입니다. `asterix-decoder v2.6.0`은
PYSEC-2021-860에 대해 "finding 0건, 검사 1건 미완료"에서 **critical (9.1)** finding으로 바뀌었고,
두 항목에 걸친 **335개** 설치 버전이 같은 방향으로 움직입니다. 그 크기에도 이 변경을 받아들이는
이유는 개수가 아니라 부류를 없애기 때문입니다 — PyPI 열거 목록에 새 junk가 들어와도 더는 advisory를
통째로 죽이지 못합니다.

**`Ranges`가 있을 때 `versions[]`를 버리는 안은 검토하고 기각했습니다.** 목록을 아예 읽지 않음으로써
154건 중 148건을 구제했을 것이고, 대체되는 그 주석도 둘 다 있을 때 목록이 중복이라고 주장했습니다.
데이터가 그것을 부정합니다. affected 항목 19,939건에 걸친 열거 항목 1,390개가 자기 항목의 범위에
포함되지 않습니다. 일부는 상류의 과잉 범위입니다 — ALPINE-CVE-2018-6196은 범위가
0.5.3_git20241203-r0에서 고쳐진다고 하면서 w3m 0.5.4-r0과 0.5.5-r0을 affected로 열거합니다 — 그러나
일부는 이 walk가 따라가지 못하는 범위를 바로잡습니다. PYSEC-2009-17은 `introduced` 하나와
`last_affected` 다섯 개를 갖고 있어 창이 첫 번째에서 닫히고, 열거 목록만이 여전히 plone 3.2와 3.3을
지목합니다. 시끄러운 놓침을 조용한 놓침으로 바꾸는 것이야말로 이 패키지가 막으려는 단 하나입니다.

### D31 — apk의 문자는 숫자 패치 레벨을 가질 수 있고, apk-tools 2.x를 따른다

apk 문법에 정확히 하나의 프로덕션이 추가됩니다. 문자 하나 바로 뒤의 숫자, 한 번:

```
digits ('.' digits)* [ letter [digits] ] ('_' suffix [digits])* ['~' hexhash] ['-r' digits]
                              ^^^^^^^^
```

`libretls 3.3.3p1-r3`, `sudo 1.7.4p6-r0`, `py3-* 0.12.5a0-r0`, `2.1a15-r17` 전부 이전 문법이
거부하던 실제 Alpine 패키지 버전입니다.

**apk-tools 두 메이저가 서로 다르고, 따라야 할 쪽은 2.x입니다.** apk-tools 2.x는 이것들을
파싱합니다. `next_token()`에 `*type == TOKEN_LETTER && isdigit(...)` 절이 명시적으로 있어
`TOKEN_DIGIT`을 내보내고, 강등 화이트리스트가 그 전이를 이름으로 허용합니다. apk-tools 3.x는
거부하며 — `token_next()`의 숫자 케이스가 `INITIAL_DIGIT`·`DIGIT`·`SUFFIX`만 나열하고
`default: goto invalid`로 갑니다 — 자기 벡터에 그렇게 단언합니다(`!0.1a1`, `!0.1bc1`).

세 가지 사실이 결정합니다. **출시된** Alpine은 전부 apk-tools 2.14.x를 싣고, 3.x는 edge에만
있습니다. Alpine은 그와 무관하게 그 버전들을 배포합니다. 그리고 3.x의 거부는 안전한 보수성이
아닙니다. `3.3.3p1-r3`와 `3.3.3p1-r2`는 양쪽이 같은 위치에서 `TOKEN_INVALID`에 닿아
`apk_version_compare_fuzzy`가 **EQUAL**을 돌려주므로, 패치되지 않은 호스트가 고쳐진 것으로
읽힙니다. 여기서 3.x를 흉내내면 그것을 들여오게 됩니다.

**새 토큰의 두 가지 성질이 load-bearing입니다.** 그것은 `apkDigit`이고 — 2.x가 쓰는 종류 —
`apkSuffix`와 `apkRevisionNo`에 대해 그 서수가 결과를 가릅니다. 그리고 `apkDigit`의 선행 0
문자열 정렬 분기에서 면제됩니다. 2.x에서 그 규칙은 `.` 뒤에 들어가는 상태인
`TOKEN_DIGIT_OR_ZERO`에 속하고, 문자 뒤 숫자는 평범한 `TOKEN_DIGIT`이기 때문입니다. 그래서
`1.0a01 == 1.0a1`이며, 문자열 정렬이라면 다르다고 답했을 것입니다.

**하드 제약은 통계가 아니라 구조로 지켜집니다.** 새 분기는 문자 바로 뒤에 숫자가 올 때만
발동하고, 그런 문자열은 전부 현재 파서의 trailing-input 검사에서 실패합니다. 오늘 파싱되는
어떤 버전도 그 분기에 닿을 수 없으므로, 오늘 올바른 어떤 순서도 바뀔 수 없습니다. apk-tools
자신의 738개 비교 벡터 파일은 여전히 736 일치, 불일치 0, 기록된 이탈 2개 그대로 재생됩니다.

**범위 규율.** apk-tools 2.x는 이 규칙보다 많이 받아들이는데, 그 초과분은 버전이 아니라
버그입니다. 2.x의 숫자 루프는 **빈** 실행을 허용해서 `1.18.-r2`와 `0.8.21.r2`가 거기서
파싱되고, 뒤엣것은 자신이 오타인 `0.8.21-r2`보다 **위로** 정렬됩니다. 두 번째 문자(`1.0a1b2`)와
패치 레벨 뒤의 점(`1.0a1.2`, 3.x가 무효로 단언)도 여전히 에러입니다. 규칙은 "문자가 패치 레벨을
가질 수 있다"이지 "2.x와 버그까지 호환한다"가 아니며, 무효 입력 표가 그 선을 이름으로 지킵니다.

**새로 생긴 과다 수용 하나는 알고 받아들입니다.** `~hash`는 이 파서가 이미 구현한 3.x 기능이라,
`1.0a1~abcd` 조합은 이제 두 레퍼런스 어느 쪽도 받지 않습니다 — 2.x에는 해시 토큰이 없고 3.x에는
문자 뒤 숫자가 없습니다. 측정한 어떤 APKINDEX·secdb·OSV 경계에도 나오지 않습니다. 이 파서는
이미 2.x/3.x 혼종이었고, 이 조합은 그 비용이며, 막는 대신 기록합니다.

**측정된 효과.** 파싱되지 않는 apk 범위 경계가 61개에서 **39개**로(패키지 30개에서 17개),
파싱되지 않는 apk 열거 버전이 **0개**로 줄었습니다 — D31이 D30 문제의 Alpine 몫을 통째로
없앱니다. `libretls 3.3.3p1-r2`와 `sudo 1.8.1p1-r0`을 담은 `alpine:3.14` 인벤토리에서 스캔은
**finding 0건, 완료하지 못한 검사 9건**에서 **high 6건, 건너뜀 0건**으로 바뀌며 CVE-2022-0778과
CVE-2019-14287을 포함합니다. CVE-2021-3156은 올바르게 빠집니다. 1.8.1p1이 그 `introduced`
경계 1.8.2보다 아래인데, 그 비교는 이전에는 시도조차 할 수 없었습니다.

**영향이 EOL 쪽에 몰려 있다는 점은 말해둘 값이 있습니다.** 해당하는 APKINDEX 항목 29개는
v3.14/main 13개와 v3.19/community 16개이고, v3.20·v3.21·v3.22의 main과 community 69,893개를
훑으면 **0개**입니다. libretls는 이제 `3.7.0-r2`입니다. 이 규칙은 오래된 이미지를 스캔할 때
의미가 있고 — 취약점 스캐너가 겨누는 대상 대부분이 그것입니다 — 앞으로 커지지 않습니다.

**살아남은 돌연변이 둘은 미검증이 아니라 등가임을 확인했습니다.** 토큰을 `apkDigit` 대신
`apkInitialDigit`으로 놓아도 표가 초록입니다. 문자 뒤 토큰은 index 2 이후에만 있고
`apkInitialDigit`은 index 0에만 있으며, 점으로 구분된 `apkDigit`은 문자 위치에서 비교가 먼저
끝나므로 마주칠 수 없습니다 — 서수 0과 1은 닿을 수 있는 모든 곳에서 같게 답합니다.
`ta.postLetter || tb.postLetter` 대 `&&`도 같은 이유입니다. 반면 `apkSuffixNo`나
`apkRevisionNo`로 바꾸면 표가 **빨개지고**, 그것이 서수 주장을 단언이 아니라 검증으로 만듭니다.

**상류 검사의 빈틈 하나를 기록해 둡니다.** 벡터 harness는 3필드 비교 줄만 읽으므로 apk-tools
master의 유효성 단언(`!0.1a1`)은 건너뜁니다. 3.x와의 의도적 이탈은 따라서 이 패키지가 가진 가장
강한 테스트에 보이지 않으며, 그 재생이 아니라 위의 논거에 기대고 있습니다.

### D32 — 접미사 없는 짧은 semver core는 축약형이며, 0으로 채운다

`parseSemVer`는 식별자가 하나나 둘인 core를 셋으로 채웁니다 — 단, 그 문자열에 pre-release도
build 접미사도 없을 때만입니다. 나머지는 그대로입니다. 선행 0은 여전히 거부, 식별자 넷 이상도
여전히 거부, 숫자가 아닌 식별자도 여전히 거부입니다.

이것은 `golang.org/x/mod/semver`가 문서화한 예외 그대로입니다 — *"vMAJOR와 vMAJOR.MINOR를
(pre-release나 build 접미사 없이) 축약형으로 인식한다"* — 그리고 govulncheck가 바로 이 경계들을
읽는 데 이미 그것에 기대고 있습니다. 데이터가 그것을 요구합니다. `github.com/canonical/lxd`는
`4.0`·`6.0`·`6.5`로, npm의 `next`는 `13.0`으로, `github.com/cosmos/cosmos-sdk`는 `0.46`으로,
`github.com/esm-dev/esm.sh`는 맨 `136`으로 쓰여 있습니다.

**접미사 없음 제한은 규칙 자체이지 세부사항이 아닙니다.** `parseSemVer`는 core를 쪼개기 **전에**
build와 pre-release를 문자열에서 떼어내므로, 그 시점에는 `4.0`과 `4.0-rc.1`이 구별되지 않습니다.
지나가는 길에 플래그로 기록해 두어야 합니다. 두 레퍼런스 모두 접미사 붙은 형태를 거부합니다 —
x/mod의 `IsValid`가 `v4.0-rc1`과 `v4.0+meta`에 대해 거짓이고, node-semver도 strict와 loose 양쪽에서
거부합니다 — 따라서 그것을 채우는 것은 어느 쪽도 하지 않는 발명입니다.

**접미사 없는 형태에 대해 두 레퍼런스가 갈리고, 여기서는 x/mod가 옳습니다.** node-semver는
`4.0`을 **버전**으로는 strict·loose 모두에서 거부하고, **범위 표현식**으로만 받아들여 `13.0`을
`>=13.0.0 <13.1.0-0`으로 읽습니다. 그 해석은 여기 적용되지 않습니다. OSV `SEMVER` 범위 이벤트는
npm 범위 문법이 아니라 단일 버전입니다. `fixed: "13.0"`은 릴리스 13.0.0을 뜻하고, 그것이 x/mod의
축약형과 node-semver 자신의 `coerce`가 똑같이 만들어내는 값입니다. 그래서 두 레퍼런스 중 하나가
그 문자열을 아예 거부함에도, 같은 규칙이 Go와 npm 양쪽에 옳습니다.

**선행 0은 검토했고 일부러 채택하지 않았습니다.** `19.03.0`(GHSA를 통한 docker/cli)과
`4.072`(neuvector/scanner)는 에러로 남습니다. node-semver는 `loose`에서도 `4.072`에 예외를
던지고, 0을 벗기지 않은 채 모양만 받아들이는 것은 거부하는 것보다 나쁩니다. `compareNumeric`은
숫자 문자열을 자릿수부터 비교하므로 `4.072`가 같은 릴리스를 가리키면서 `4.72`보다 **위로**
정렬됩니다. 그것이 조용한 순서 뒤바뀜이고, 이 슬라이스가 피하려는 거래입니다. 따라서
`github.com/docker/cli`는 시끄러운 건너뜀으로 남습니다.

**식별자 넷 이상은 채우기와 반대 이유로 에러로 남습니다.** 강제 변환은 `1.2.3.4`를 `1.2.3`으로
읽는데, 그것은 빠진 성분을 채우는 것이 아니라 있는 성분을 버리는 것입니다.

**OSV 센티널은 이름으로 제외합니다.** `"0"`은 식별자 하나짜리 접미사 없는 core라서 그냥 두면
`0.0.0`으로 채워지는데, 그것은 그 값의 뜻이 아닙니다 — 범위 계층이 그것을 음의 무한대로
해석하고, `0.0.0`으로 읽으면 모든 `0.0.0-prerelease` 빌드보다 **위로** 정렬되어 그것들을 창
밖으로 떨어뜨립니다. 이 보호는 지금 완화하는 세-식별자 검사에서 공짜로 따라오던 것이므로,
그 검사를 완화하면 보호를 의도적으로 되살려야 합니다. 기존 무효 입력 테스트가 이미 `"0"`을 바로
그 근거와 함께 적어두고 있었고, 그것이 이 문제를 잡았습니다.

**하드 제약은 구조로 지켜집니다.** 채우기는 오늘 파서가 에러를 내는 곳에서만 발동하므로, 지금
파싱되는 어떤 버전도 비교 키나 다른 버전에 대한 순서가 바뀔 수 없습니다.

**측정된 효과.** 파싱되지 않는 semver 범위 경계가 96개에서 **40개**로(패키지 42개에서 19개)
줄었습니다. 남은 것은 선행 0 부류와 `2.10-rc2`·`9.6.0b1` 같은 진짜 기형입니다. `lxd v5.0.2`,
`cosmos-sdk v0.45.9`, `next 12.3.0` 인벤토리에서 스캔은 **finding 29건에 평가 불가 advisory
8건**에서 **finding 34건에 건너뜀 0건**으로 바뀌며, `next`가 critical인 CVE-2025-29927에
닿는 것을 포함합니다.

돌연변이 여섯 개가 red로 확인됐습니다. 채우기 제거, 접미사 없음 가드 제거, 센티널 가드 제거,
`0` 대신 `1`로 채우기, 식별자 둘짜리만 채우기, 그리고 식별자 넷짜리를 통과시키기.

### D33 — 가장 좁은 KISA 공지가 이기고, 그 폭을 공개한다

보강은 `(CVE, Source)`로 키가 잡히고 모든 KISA 레코드의 source가 같으므로, 공지 둘이 지목한 CVE는
나중에 도착한 페이지 쪽만 남았습니다. 2026-08-06 라이브로 측정하니 `convert`는 CVE 18,524개에 대해
**20,315**개 레코드를 만듭니다. **1,791**개가 페이지 순서로 정해지고 있었고, 그것은 D25가 문장
그대로 금지하는 동점 처리입니다.

이제 승자는 CVE를 **가장 적게** 지목한 공지이고, 동수면 공지 URL로 끊습니다. 이 동점 처리는 일부러
자의적입니다 — 요점은 그것이 네트워크의 성질이 아니라 규칙이라는 데 있습니다.

**선택은 저장소가 아니라 provider에서 일어납니다.** 각 공지가 몇 개의 CVE를 지목했는지는 그 walk만
알고, 규칙은 코퍼스 전체를 필요로 합니다. 페이지가 도착하는 대로 내보내면 더 좁은 공지가 아직 남아
있는지 알 수 없습니다. 그래서 walk가 끝나기 전에는 아무것도 내보내지 않고, 도중에 실패한 walk는
읽어낸 절반에서 고른 승자 대신 아무것도 내보내지 않습니다 — 그것은 규칙의 옷을 입은 도착 순서
결함일 뿐이기 때문입니다.

**이것은 저장소의 일이 아니며, D13의 평소 논거가 여기엔 적용되지 않습니다.** 무손실 저장은 나중에
필드를 더할 때 재빌드를 피하려고 있는데, 보강은 매 `db build`마다 1분 미만에 처음부터 다시
만들어지고 seed로 이월되지도 않습니다. D13이 막으려는 재빌드가 여기서는 공짜이므로, 진 쪽을
보관해도 얻는 것이 없습니다.

**롤업 문제는 해결이 아니라 공개되며, 그 근거는 측정입니다.** 이 슬라이스를 열 때 기록한 예상은
가장 좁은 공지가 이기면 도착 순서 의존과 롤업 희석이 함께 사라진다는 것이었습니다. 앞의 절반만
참입니다. 선택 이후에도 **18,524개 중 12,972개(70%)** 가 여전히 CVE 20개 초과를 지목한 공지에서
나오고, 그 CVE만 지목한 공지에서 나오는 것은 **822개(4%)** 뿐입니다 — 대부분의 CVE에게 월간 공지가
그것을 지목하는 **유일한** 공지이기 때문입니다. 더 좁은 것이 있어야 고를 수 있습니다.

그래서 완화 수단은 공개입니다. `Enrichment.Claims`가 그 공지가 지목한 CVE 수를 기록하고,
`--explain`은 하나를 넘을 때 `scope: this notice covers N vulnerabilities, not only this one`을
찍으며, JSON 문서가 `claims`를 실어 나릅니다(스키마 3). 그것이 없으면 천 개의 CVE를 지목한 공지와
이 CVE에 대해 쓰인 산문이 똑같이 렌더링되고, 독자는 자기가 무엇을 보고 있는지 알 방법이 없습니다.
**넓은 공지를 아예 버리는 안은 기각했습니다.** 표현 문제를 고치자고 코퍼스의 70%를, 그 CVE들이
가진 유일한 한국어 텍스트를 함께 버리는 일이 되기 때문입니다.

**`Provenance.Records`는 `convert`가 만든 수가 아니라 데이터베이스가 담을 수를 보고합니다.** 더 큰
수를 보고하면 선택이 버린 레코드만큼 정확히 과다 주장하게 되고, 그것이 지금 고치는 대상입니다
(D20의 규칙을 enricher에 적용한 것).

**세 번째 결함은 결함이 아닌 것으로 판명됐습니다.** 레코드 2,202개(12%)가 개요 없음 폴백에서
시작하는 요약을 담고 있어 파서 실패처럼 읽혔습니다. 라이브 공지 100건으로 측정한 결과, 정확한
`□ 개요` 제목은 65건에 있고 느슨한 `□ …개요` 형태로는 67건이며, 나머지 33건은 개요 절이 아예
없습니다. 그 33건에는 폴백이 맞는 답이지 놓침이 아니고, 제목 매칭을 넓히는 것은 백에 둘을 얻자고
모든 건에 오탐 위험을 지우는 일입니다. 의도적으로 그대로 둡니다.

돌연변이 여섯 개가 red로 확인됐습니다. 첫 공지 승리, 마지막 공지 승리, 가장 넓은 공지 승리,
보고되지 않은 폭을 가장 좁은 것으로 취급하기, 선택 이전 개수를 `Records`로 보고하기, 그리고
`Claims`를 채우지 않기. 리포트 픽스처는 `Claims`를 그 픽스처 어디에도 없는 값으로 설정합니다.
int를 0인 채로 두면 그 필드를 전혀 읽지 않는 렌더러도 바이트 단위로 같은 출력을 낼 수 있기
때문입니다.

### D34 — semver core의 선행 0은 거부가 아니라 정규화한다

선행 0이 붙은 core 식별자를 받아들이고 벗겨냅니다. `19.03.0`은 `19.3.0`과 같게 비교됩니다.
node-semver의 loose 모드이고, 7.8.1에 대고 실측했습니다 —
`SemVer("19.03.0", {loose:true}).version === "19.3.0"`,
`eq("19.03.0", "19.3.0", {loose:true}) === true`.

**받아들이는 것과 정규화하는 것은 둘이 아니라 하나의 규칙입니다.** D32가 이 모양을 받아들이지
않은 이유가 바로 그것이었습니다. 받아들이기만 하면 거부하는 것보다 나쁩니다. `compareNumeric`이
숫자 문자열을 값보다 자릿수로 먼저 비교하므로, `4.072.0`이 같은 릴리스를 가리키면서 `4.72.0`보다
**위로** 정렬됩니다 — 시끄러운 건너뜀 자리에 조용한 순서 뒤바뀜이 들어섭니다. 벗겨내는 것이
받아들이기를 안전하게 만들고, 그래서 테스트 표에 자릿수는 다르고 값은 같은 쌍이 들어 있습니다.
그 모양만이 둘을 구별할 수 있습니다.

**`golang.org/x/mod/semver`와의 의도적 이탈입니다.** x/mod는 선행 0을 아예 거부합니다.
`19.03.9`는 Go 자신의 버전 규칙으로는 표현할 수 없는 실제 Docker 태그이고 — docker가 애초에
`+incompatible`로 실리는 이유의 일부입니다 — 이 문자열은 무언가가 해석한 모듈 버전이 아니라
릴리스를 서술하는 GHSA 범위 경계로 우리에게 옵니다. 여기서 x/mod를 따르면
`github.com/docker/docker`, `github.com/moby/moby`, `github.com/docker/cli`가 영구히 평가
불가로 남고, 그것은 node-semver가 주는 답보다 나쁜 답입니다.

**D32의 축약형으로 확장하지 않습니다.** `4.072`와 `01.0`은 에러로 남습니다. 두 규칙은 서로 다른
레퍼런스에서 왔고 어느 레퍼런스도 둘을 동시에 적용하지 않습니다. node-semver의 loose **파서**는
식별자 셋을 요구해서 `4.072`에 예외를 던지고, x/mod의 축약형은 선행 0을 허용하지 않습니다.
`4.072`를 `4.72.0`으로 읽는 것은 `coerce()`뿐인데, coerce는 `1.2.3.4`를 조용히 `1.2.3`으로
잘라내기도 하는 더 손실이 큰 진입점입니다. pre-release 식별자가 스펙 §9 규칙을 그대로 지키는
것도 같은 이유입니다. 데이터가 그 이상을 요구하지 않습니다.

**pep440 관용보다 이것을 고른 기준은 개수가 아니라 빈도입니다.** 남은 것만 보면 pep440이 더
큽니다(당시 경계 45 대 40). 그러나 그쪽은 `buildbot`, `trac`, `neutron`, `asterix-decoder` —
실제 인벤토리에 잘 없는 패키지들입니다. semver 쪽은 `docker/docker`, `moby/moby`, `go-redis`,
`argo-cd`, `grafana`였습니다. 경계 하나의 값어치는 그것이 물릴 때의 비용이고, 이쪽이 물립니다.

**측정된 효과.** 파싱되지 않는 semver 범위 경계가 40개에서 **12개**로, 패키지 19개에서
**11개**로 줄었습니다. 경계 수가 시사하는 것보다 큰 감소인데, `19.03.x`가 docker와 moby의 여러
advisory에 걸쳐 반복되기 때문입니다. `assay`가 자기 바이너리를 스캔하면 이제 **평가하지 못한
패키지가 하나도 없습니다.** 전에는 `github.com/docker/cli`를 건너뛰었습니다.
`v29.5.3+incompatible`은 19.03에서 끝나는 범위에 대해 올바르게 finding이 아닙니다.

남은 것은 관습이 다른 정도가 아니라 진짜 기형입니다. `9.6.0b1`(go-redis), `2.10-rc2`(argo-cd),
`3.0-beta1`(grafana)은 semver가 요구하는 하이픈이 빠져 있고, `2018-05-19`는 날짜이며,
`1.0.25.1`과 `0.4.4.3`은 식별자가 넷입니다. 하이픈이 들어갈 자리를 추측하는 것은 0으로 채워진
숫자를 읽는 것과는 다른 결정이고, 따를 레퍼런스가 없습니다.

돌연변이 다섯 개가 red로 확인됐습니다. 선행 0을 다시 거부하기, 정규화 없이 받아들이기, 채워진
core 가드 제거하기, 전부 0인 식별자를 빈 문자열까지 깎기, 그리고 pre-release 식별자에도 선행 0
허용하기.

### D35 — 누구의 데이터가 읽히지 않는지 밝히고, 문서화된 오타 하나를 수집 시점에 고친다

세 comparer를 통틀어 아직 파싱되지 않는 범위 경계가 96개입니다. 그 96개 전부가 파싱 가능한 다른
경계를 가진 range 안에 있으므로, 질문은 "정보가 있느냐"가 아니라 "그것으로 무엇을 결론지어도
되느냐"였습니다. 변경 둘, 그리고 데이터로 기각한 안 하나.

**누구의 데이터가 잘못인지 말합니다.** 기형인 advisory 경계와 읽히지 않는 설치 버전이 둘 다
`not evaluated`로 렌더링됐는데, 독자에게 정반대의 뜻입니다. 앞은 손쓸 수 없는 것이고 뒤는 보통
자기 인벤토리입니다. 둘은 이미 구조적으로 갈라져 있습니다 — `sortEvents`가 walk 시작 전에 모든
경계를 검증하고, 검증할 필드를 고르는 우선순위가 walk가 비교할 필드를 고르는
introduced/fixed/last_affected 우선순위와 같습니다 — 그래서 walk 안의 실패는 설치 버전일 수밖에
없습니다. 이 불변식이 결정적인데 어디에도 적혀 있지 않았습니다. 이제 양쪽이 볼 수 있는 자리에
적었습니다. `eventVersion`의 우선순위를 바꾸면 검증되지 않은 경계가 walk에 들어가고, 그러면
메시지가 advisory의 결함을 패키지 탓으로 돌리게 됩니다.

```
libdwarf 0.5.0-r0 (ALPINE-CVE-2015-8538):
  the advisory's range bound "1999-12-14" could not be read: …
github.com/gogo/protobuf 1.3-broken (GHSA-c3h9-896r-86jm):
  this package's own version "1.3-broken" could not be read, comparing it against
  the advisory's fixed bound "1.3.2": …
```

matcher의 `comparing <version>:` 접두사도 함께 없앴습니다. 패키지와 그 버전이 이미 렌더링된 줄의
머리에 있고, 모든 메시지 앞에 설치 버전을 붙이면 원인이 advisory인 메시지 앞에도 그 문자열이
놓입니다 — 없애려던 바로 그 혼동입니다.

**Alpine의 `.rN`을 `-rN`으로, 수집 시점에 고칩니다.** v7 데이터베이스 기준 **11**개 경계이고,
그곳의 apk `fixed` 실패는 전부 세 문자열 중 하나입니다 — `0.8.21.r2`(irssi, 6회),
`10.2.24.r0`과 `10.2.22.r0`(mariadb, 5회), Alpine v3.3~v3.8.

수집 시점인 것은 D16의 이유(어떤 질의 경로도 잊을 수 없게)이고, comparer가 **아닌** 것은 D31의
이유입니다. apk-tools 2.x는 빈 숫자 실행 허용을 통해 `0.8.21.r2`를 파싱하고, 그것이 오타인
`0.8.21-r2`보다 **위로** 정렬합니다. 문법에 이 문자열을 가르치는 것은 그 순서를 받아들이거나, 그
문자열을 읽는 유일한 레퍼런스와 모순되거나 둘 중 하나입니다. 오타라고 부르고 데이터를 고치는 것이
실제로 일어나는 일에 대한 정직한 서술입니다. D31이 이미 그 해석을 이 문서와 무효 입력 표에
기록해 두었으므로, 새로 주장하는 것은 없습니다.

가드 둘이 이것을 지탱합니다. 원본이 파싱되지 않아야 하므로 이미 유효한 것은 결코 다시 쓰이지
않고, 치환 결과가 파싱되어야 하므로 실패한 수리는 원본을 그대로 두어 에러가 이 코드가 지어낸
문자열이 아니라 상류가 실제로 배포한 것을 지목합니다.

**이것은 상류가 배포하지 않은 것을 쓰는 일이고**, D13에 대한 실제 비용입니다. EOL 패키지 두 개의
경계 열한 개에 대해 대안이 더 나빴습니다. 두 형태를 모두 저장하면 모든 독자가 복잡해지고,
`Convert`·`Fetch`·`Provider` 인터페이스로 수리 개수를 빼내는 것은 시그니처 변경 셋입니다. 대신
얻은 가시성은, 규칙이 순수 함수 하나 안의 치환 하나이고 영향받는 집합이 표로 못박혀 있다는
것입니다 — "이게 무엇을 바꿨나"에 신뢰가 아니라 읽기로 답할 수 있습니다. 수리 대상이 한 줌을
넘어서거나 두 번째 치환이 제안되면 그 거래는 성립을 멈추고 개수를 배관해야 합니다.

**부분 평가는 검토하고 데이터로 기각했습니다.** 명백해 보이는 규칙 — 파싱되지 않는 `introduced`를
`0`으로 취급하라, 창을 넓히는 것은 미탐을 만들 수 없으니 — 이 가장 큰 단일 사례에 반증됩니다.
Alpine의 imagemagick 레코드 18회는 `introduced 7.0.0-0`(읽히지 않음) 옆에
`fixed 6.9.6.8-r0`(정상)을 갖고 있습니다. introduced가 fixed보다 **위**입니다. 그것을 `0`으로
바꾸면 창이 넓어지는 게 아니라 `[7.0.0, ∞)`에서 `[0, 6.9.6.8)`으로 **뒤집혀서**, 그 레코드가
덮으려던 7.x 전체를 잃습니다. 더 조심스러운 판본 — "파싱 가능한 경계만으로 답이 강제될 때만
답하라" — 도 같은 반론에 무너집니다. imagemagick 7.0.1에 대해 range는 문법상 *영향 없음*을
강제하는데, 그것이 자신 있는 틀린 답이고 이 도구가 존재하지 않게 하려는 단 하나입니다.

그래서 apk 28개, pep440 45개, semver 12개가 시끄러운 건너뜀으로 남습니다. 읽을 방법이 없는
데이터에 대해서는 그것이 옳은 동작입니다. 돌연변이 여섯 개가 red로 확인됐고, 둘은 등가로
살아남아 `repair.go`에 기록했습니다. 유효한 apk 버전은 `.r`을 포함할 수 없으므로 이미-파싱됨
가드는 답을 바꿀 수 없고, `LastIndex` 대신 `Index`도 두 번째 가드가 뒤에 남은 `.r`을 거부하는
이상 답을 바꿀 수 없습니다.

## 3. 아키텍처

### 측정된 데이터 규모

2026-07-29에 실제 OSV 덤프로 측정. 이 수치들이 D4(bbolt), D15(`MAL-*` 제외), D17(미평가 심각도)이
서 있는 근거입니다. 그중 어느 것이든 재검토하기 전에 **다시 측정하십시오.**

| 생태계 | 취약점 레코드 | 크기 | `MAL-*` 레코드 | 크기 |
|---|---:|---:|---:|---:|
| Go | 8,599 | 22.1 MB | 18 | 0.0 MB |
| npm | 7,004 | 19.2 MB | 216,865 | 323.2 MB |
| PyPI | 13,010 | 44.9 MB | 11,579 | 20.1 MB |
| **슬라이스 1 합계** | **28,613** | **86.2 MB** | **228,462** | **343.3 MB** |

크기는 비압축 JSON 기준입니다. 슬라이스 1의 압축 다운로드는 필터링 여부와 무관하게 약 244 MB.

이후 슬라이스용: Alpine 4,401건(압축 3.8 MB), Debian 압축 64 MB, Ubuntu 압축 570 MB.
46개 생태계 전체는 대략 압축 1.5 GB.

권고 28,613건에 86 MB라면 bbolt + JSON 값이 여유 있게 들어갑니다. 필터링하지 않은 257,075건
430 MB라도 동작합니다 — **어느 쪽이든 이 결정에는 상당한 여유가 있습니다.**

**OSV에 Red Hat 데이터가 존재합니다**(압축 25 MB). RHEL 데이터가 없거나 무시할 만하다는 이전
가정과 배치됩니다. 정확한 RHEL 매칭에 필요한 만큼 백포트를 반영하는지는 별개 문제이며, 그 작업을
시작할 때까지 미해결로 둡니다.

### 파이프라인

```
target (image | binary | dir | SBOM file)
  │
  ├─▶ Source      open the target for file access; carries layer provenance
  ├─▶ Cataloger   files → []Package, one per ecosystem
  ├─▶ Target{Distro, []Package}          ◀── normalized inventory
  ├─▶ Matcher     Package × Store → Finding, using per-ecosystem Comparer
  ├─▶ Enricher    join KISA data by CVE ID
  └─▶ Reporter    table / JSON / SARIF, --fail-on
```

데이터베이스는 이 흐름과 직교하며 스캔 중에는 읽기 전용입니다:

```
Provider(OSV)  ─┐
                ├─▶ []Advisory ─▶ Store          written only by `assay db update`
Provider(KISA) ─┘                    ▲
                                     └── Matcher reads
```

### 인터페이스

| 인터페이스 | 책임 | 구현체 |
|---|---|---|
| `Source` | 타깃을 열어 파일 접근 제공 | image, dir, file, binary |
| `Cataloger` | 파일 → `[]Package` | apk, dpkg, cyclonedx, go-mod, go-binary, npm, jar |
| `Store` | 권고 조회 | bbolt |
| `Comparer` | 한 생태계 안에서의 버전 순서 | semver, PEP 440, apk, deb, rpm |
| `Provider` | 업스트림 피드 → `[]Advisory` | OSV, KISA |

새 생태계를 지원한다는 것은 `Cataloger` 하나와 `Comparer` 하나를 쓰는 것입니다. 나머지는 바뀌지
않습니다 — **이 분해 전체가 존재하는 이유가 바로 그 성질입니다.**

```go
type Store interface {
    Lookup(ecosystem, name string) ([]Advisory, error)
    LookupBySource(ecosystem, sourceName string) ([]Advisory, error)  // D8
    Enrichment(id string) (*Enrichment, error)
    Meta() (Meta, error)
    Close() error
}

type Comparer interface {
    Compare(a, b string) (int, error)  // D9
}

type Provider interface {
    Fetch(ctx context.Context) ([]Advisory, Provenance, error)
}
```

### 핵심 타입

```go
type Target struct {
    Distro   *Distro    // from /etc/os-release; nil for language-only targets  (D7)
    Packages []Package
}

type Package struct {
    Name, Version, Type string        // Type: apk | deb | golang | npm | pypi | maven
    PURL      string
    Source    *SourcePackage          // source package, for indirect matching  (D8)
    Locations []Location              // which file and layer it came from
}

type Advisory struct {                // OSV shape  (D1)
    ID       string                   // CVE-… | GHSA-… | GO-… | ALPINE-… | KVE-…
    Aliases  []string                 // OSV `aliases`  ─┬─ both carry the CVE↔KVE join (D3)
    Upstream []string                 // OSV `upstream` ─┘
    Source   string                   // "osv" | "kisa" — provider provenance
    Kind     Kind                     // vulnerability | malicious  (D15)
    Affected []Affected
    Severity []Severity               // stored as CVSS vectors, banded at query time (D13)
}

type Affected struct {
    Ecosystem string                  // "Go" | "Alpine:v3.19"  (D6)
    Name      string
    Ranges    []Range                 // introduced / fixed events
}

type Finding struct {
    Package  Package
    Advisory Advisory
    Evidence Evidence                 // which range, which comparer, what result  (D10)
}
```

### 저장소 레이아웃

```
<os.UserCacheDir()>/assay/db/v7/vulnerability.db      override: ASSAY_DB_DIR

buckets:
  advisories   "<ecosystem>\x00<name>"     → []AdvisoryID  primary lookup
  by-source    "<ecosystem>\x00<source>"   → []AdvisoryID  indirect matching (D8)
  by-id        "<advisory-id>"             → Advisory      the record itself, stored once
  enrichment   "<cve-id>"                  → Enrichment    KISA (D3)
  meta         "schema" | "built-at" | "providers"
```

**조회 버킷은 레코드가 아니라 권고 ID를 담습니다.** 한 권고가 여러 패키지에 영향을 주는 일이
흔합니다 — Go 덤프 측정 결과 8,510건 중 1,452건이 둘 이상의 패키지를 지목하고, 최대 22개입니다 —
그래서 패키지를 키로 레코드를 직접 저장하면 같은 것이 반복 저장됩니다. 측정된 증가율은 1.44배이고,
`by-id`가 자체 사본을 갖는 것까지 합치면 순진한 레이아웃은 21.9 MB 데이터를 53.6 MB로 만듭니다.
ID를 `by-id`로 해석하는 데 점 조회가 한 번 더 들지만 마이크로초 단위입니다.

| OS | 경로 |
|---|---|
| Windows | `%LocalAppData%\assay\db\v7\` |
| macOS | `~/Library/Caches/assay/db/v7/` |
| Linux | `~/.cache/assay/db/v7/` (`XDG_CACHE_HOME` 존중) |

값은 JSON으로 시작합니다. 스캔당 수백 번 조회 기준으로 bbolt 읽기는 마이크로초이고 디코딩이
지배적이지만 그래도 수십 밀리초 수준입니다. 인코딩은 `Store` 뒤에 가려져 있어 호출자를 건드리지
않고 바꿀 수 있습니다.

`db update`는 임시 파일에 빌드한 뒤 실행 중인 데이터베이스 위로 rename하므로, 동시에 도는 스캔이
부분 기록을 보지 않습니다. **Windows에서는 대상이 열려 있으면 rename이 실패합니다** — 알려진 함정
문서 참조.

## 4. 전달 슬라이스

아키텍처 계층이 아니라 **동작하는 경로**를 따라 잘랐습니다. 계층 하나만으로는 실행할 수 없고,
실행할 수 없는 설계는 검증할 수 없습니다.

### 슬라이스 1 — 매칭 코어 ← 첫 구현 계획 대상

```
CycloneDX SBOM ──▶ Package ──▶ Store(bbolt) ──▶ Matcher ──▶ table
                                   ▲
                           OSV provider (Go / npm / PyPI)
```

**완료 기준**

- `assay db update`가 OSV 언어 생태계 덤프로 로컬 데이터베이스를 빌드한다
- `assay db status`가 provider별 `DataAsOf`와 레코드 수를 출력한다
- `assay scan sbom.cdx.json`이 매칭된 CVE를 table로 출력한다
- 데이터베이스가 없으면 안내와 함께 2로 종료한다 — 빈 클린 결과를 내지 않는다
- `Comparer`가 semver와 PEP 440 엣지 케이스를 다루는 표 기반 테스트를 갖는다
- 같은 SBOM에 대한 grype 대조 검증(§5)

**여기서 확정되는 것:** 핵심 타입 전체, `Store` / `Comparer` / `Provider` 인터페이스, 종료 코드
우선순위, 출처 기록.

### 슬라이스 2 — 컨테이너

`assay scan alpine:3.19`. 레지스트리 pull → 레이어 추출 → `/etc/os-release` →
`/lib/apk/db/installed` → `Alpine:vX.Y` 조회.

**설계 리스크가 가장 큽니다.** `Target.Distro`, 릴리스가 포함된 생태계 키, `Location`의 레이어
출처가 전부 여기서 처음 현실과 만납니다. 늦추지 않고 앞에 두는 이유가 그것입니다 — **설계가
틀렸다면 빨리 아는 편이 쌉니다.**

**완료 기준:** Alpine 이미지가 끝에서 끝까지 스캔되고, 레이어 digest가 `Location`에 나타나고,
apk `Comparer`가 표 기반 테스트를 통과하고, grype 대조가 성립할 때.

### 슬라이스 3 — 파일시스템과 바이너리 타깃

`debug/buildinfo`(표준 라이브러리만)를 통한 `assay scan ./bin/assay`, 그리고 `go.mod`를 통한
`assay scan dir:./project`.

**어디든 끼워 넣을 수 있습니다.** 슬라이스 2에도 4에도 의존하지 않고, 비용이 매우 작으면서
`Source` / `Cataloger` 추상화를 두 번째 구현체로 검증합니다. 슬라이스 2가 막히면 이쪽이
우회로입니다.

**완료 기준:** assay가 자기 자신의 바이너리를 스캔할 때.

### 슬라이스 4 — 판정과 출력

`--fail-on`, `--fail-on-unknown`, JSON / SARIF, explain 모드. **종료 코드 1이 처음으로 도달
가능해지는 지점입니다.** 저장된 CVSS 벡터로부터의 심각도 밴드 계산이 여기 들어오며(D13), 슬라이스
1이 아직 쓰지 않는 벡터를 저장해 두는 이유가 이것입니다.

**완료 기준:** 출력이 결정적이고 diff 가능하며, explain 모드가 특정 finding의 `Evidence`를 출력할
때.

### 슬라이스 5 — KISA 보강

KNVD provider → `enrichment` 버킷 → CVE ID 조인 → 리포트의 한국어 설명과 심각도.

**2026-08-02에 선행 조건을 조사했고, 해소되지 않았습니다.** 막고 있던 질문은 KNVD가 기계 판독
가능한 인터페이스를 제공하는가와 약관이 재배포를 허용하는가였습니다. 둘 다 부정적이고, 그보다
중요한 세 번째 발견이 있습니다.

**2026-08-03 정정. 위 측정은 틀린 질문에 답했습니다.**

물었던 것은 KNVD가 독립 *매칭* 소스가 될 수 있는가였습니다. KNVD 자체 취약점 공개가 assay가
스캔하는 패키지를 다루는가. 다루지 않고, 그 부분은 그대로 유효합니다.

그런데 KNVD에는 게시판이 둘이고, 슬라이스는 작은 쪽을 봤습니다. `공개된 취약점`은 KISA가 직접
공개한 것으로 173건이고 국내 상용 소프트웨어입니다. `보안공지`는 국내 기관에 실제로 쓰는
소프트웨어의 CVE를 패치하라고 알리는 보안 공지이며 **2,422건**입니다. 그 게시판에서 표본:

```
Apache 제품 보안 업데이트 권고    CVE-2026-23918   Apache HTTP Server 2.4.66 -> 2.4.67
OpenSSL 취약점 보안 업데이트 권고  CVE-2025-11187   OpenSSL 3.4.x/3.5.x/3.6.x
                                CVE-2025-15467   OpenSSL 3.0.x ~ 3.6.x
```

CVE를 키로 하고, 영향 버전과 해결 버전, 한국어 제목과 본문이 있습니다. 실제 데이터베이스에
맞춰본 결과 셋 다 assay가 이미 가지고 있는 권고이고, 실제 컨테이너에 들어가는 패키지입니다.

| KISA 공지 | 우리 레코드 | 패키지 |
|---|---|---|
| CVE-2026-23918 | `ALPINE-CVE-2026-23918` | `apache2`, Alpine v3.20–v3.24 |
| CVE-2025-11187 | `ALPINE-CVE-2025-11187` | `openssl`, Alpine v3.22–v3.24 |
| CVE-2025-15467 | `ALPINE-CVE-2025-15467` | `openssl`, Alpine v3.17–v3.24 |

즉 **CVE 기반 보강 조인이 걸립니다.** D27이 NVD에 대해 이미 만드는 모양 그대로입니다. assay가
OSV로 매칭하고, 같은 CVE에 대해 다른 권위가 무엇을 말했는지를 붙입니다. KISA가 더해주는 것은
한국어 제목, 한국어 설명, 그리고 KISA가 국내 기관에 조치하라고 알렸다는 사실입니다. 다른 어떤
스캐너도 담고 있지 않은 것들입니다.

바뀌지 않은 것: KNVD를 독립 매처로 쓰는 것은 여전히 성립하지 않고, 접근 경로도 여전히 나쁩니다
(`knvd.krcert.or.kr` 딥링크는 평범한 요청에 404를 반환하고, 같은 공지를 서비스하는
`boho.or.kr`은 읽힙니다). 라이선스 문제도 미해결입니다. 푸터가 공공누리 표시 없이 모든 권리
보유이며, 이는 만들어진 데이터베이스를 재배포할 때 문제가 됩니다(*KISA 데이터를 별도 아티팩트로
분리* 항목 참조).

아직 재지 않은 것: 2,422건 중 일반적인 스캔과 겹치는 비율. 표본 3건은 3건 다 걸렸지만 무작위
추출이 아니라 검색에서 떠오른 셋입니다.

**2026-08-03, 수집된 코퍼스로 측정.** ssk가 이미 보안공지 게시판을 구조화된 JSON으로 모아두었습니다.
공지 2,039건이고 각각 `cve_id`, `product`, `problem_version`, `solved_version`이 파싱되어 있으며
한국어 제목과 본문도 있습니다. 첫 조사가 열어둔 접근 경로 문제가 이것으로 해결되고, 그때 낼 수 없었던
숫자도 나옵니다. **고유 CVE 17,003개**입니다.

실제 데이터베이스(권고 32,046건)와 조인한 결과:

| | |
|---|---|
| assay도 가지고 있는 KISA CVE | **413 (KISA의 2.4%)** |
| 그중 `Alpine`에서 도달 가능 | 279 |
| `Go` / `npm` / `PyPI` | 56 / 56 / 37 |
| 그 외 | 16 |

조인은 걸리고, 게시판 규모가 시사하는 것보다는 작습니다. KISA 코퍼스는 데스크톱과 엔터프라이즈
소프트웨어에 몰려 있습니다 — MS 제품 항목 9,968건, Adobe 1,985건, Cisco 921건 — assay가 스캔하지
않는 것들입니다. 겹치는 것은 서버 쪽 롱테일입니다. OpenSSL, Apache, Exim, Mozilla.

Alpine 권고 약 4,405건 대비 279건이면, finding 16건 중 1건 정도가 한국어 제목과 조치 정보를
갖게 됩니다. 실재하는 기능이고 동시에 소박한 기능입니다. "국내 취약점 데이터"라고 추상적으로 적기
보다 그렇게 적는 편이 맞습니다.

**접근 경로는 ssk가 만든 크롤러**(`make-kisa-rule/main.py`)**로 이미 해결되어 있습니다.** 위 코퍼스가
거기서 나왔습니다. KNVD의 SPA에는 문서화되지 않았지만 동작하는 JSON API가 있습니다.

```
POST /api/core/pu/view/count/get        -> 전체 공지 건수
POST /api/core/pu/view/vuln-notice/get  -> 페이지네이션 목록
     {"collectionType":"VULNOTICE","tabs":"ko","skipCount":N,"limit":50, ...}
```

목록 응답이 이미 `content`와 `content_html`을 담고 있어서 공지별 상세 요청이 필요 없습니다.
`detailSecNo.do` 딥링크가 404를 반환하는 것이 문제가 되지 않았던 이유입니다. 게시일은 필드로
노출되지 않으며, 크롤러는 Mongo ObjectId 앞 4바이트(문서 생성 타임스탬프)에서 복원합니다.

그 크롤러에서 이 저장소로 그대로 옮겨오지 못한다고 기록됐던 것이 둘 있고, 둘 다 세부가 아니라
결정으로 다뤄졌습니다.

- TLS 검증을 끕니다(`verify=False`). 취약점 스캐너가 인증서 검증을 끄려면 "동작했다"보다 강한
  이유가 필요하므로, 그 엔드포인트가 실제로 그것을 요구하는지 먼저 확인해야 합니다.
- 영향/해결 버전 표를 BeautifulSoup으로 `content_html`에서 파싱합니다. 이 저장소는 서드파티
  의존성을 두지 않고 Go 표준 라이브러리에는 HTML 파서가 없으므로, 언뜻 `poetry.lock`이 강제했던
  것과 같은 선택으로 보였습니다.

**둘 다 실재하지 않았고, 그것을 알아낸 방법은 한 번은 말해둘 가치가 있습니다. 문서를 읽는 대신
서비스를 직접 호출한 것입니다.** 2026-08-05, 라이브 엔드포인트로 측정:

- `https://knvd.krcert.or.kr/`는 엄격하게 검증됩니다 — `Verify return code: 0 (ok)`,
  DigiCert가 발급한 인증서, HTTP 200. 참조 크롤러의 `verify=False`는 필요해서가 아니라
  방어적으로 넣은 것이었습니다. 이 저장소는 평범한 TLS를 쓰고 `InsecureSkipVerify`는 어디에도
  설정하지 않습니다.
- 목록 응답은 `content_html`과 나란히 `content_text`를 담고 있습니다 — 이미 태그 없는 순수
  텍스트라 파서가 아예 필요 없습니다. 참조 크롤러가 `content_html`을 BeautifulSoup으로 훑는
  것은 영향/해결 *버전 표*를 구조화된 규칙으로 만들기 위해서인데, D3이 이미 보강에는 그것이
  필요 없다고 못 박아 두었습니다. 제목, 요약, 링크뿐이지 매칭 소스가 아닙니다.

라이브 서비스가 정리해 준 것이 둘 더 있습니다. 둘 다 처음부터 예상하지 못했고, 문서를 읽어서 알아낸
것도 아닙니다.

- **KISA 자체 count 엔드포인트는 동작하지 않습니다.** `POST /api/core/pu/view/count/get`을
  목록 요청과 같은 본문, 그리고 더 짧은 본문 세 가지로 찔러봤는데 넷 다
  `{"resType":"RES_ERROR","resMsg":"…"}`로 답했습니다. `totalResults`에 맞춰 페이지를 도는
  `nvd`와 달리 맞춰볼 총량이 없습니다. 그래서 걷기는 목록 응답만으로 자신의 끝을 알아내야
  합니다. 첫 페이지 이후 처음 나오는 빈 페이지에서 멈추고, `skipCount` 0에서의 빈 페이지는
  (재시도하는 대신) 거부합니다 — 수천 건짜리 코퍼스의 진짜 끝일 수 없기 때문입니다.
- **KNVD는 자신의 실패를 HTTP 200과 빈 목록으로 보고합니다** — 코퍼스의 끝이 취하는 것과 똑같은
  모양입니다. 응답 자체의 `resType` 필드를 확인하지 않으면 걷는 도중의 서비스 장애와 끝에 도달한
  것을 구분할 수 없고, 크게 실패하는 대신 동기화를 조용히 잘라먹게 됩니다.

**KNVD 자체 취약점 레코드는 173건이고, 그중 assay가 스캔하는 생태계에 속한 것은 하나도
없습니다.** `공개된 취약점` 전체가 173건이며 2024년 이후 월 1~2건 속도로 발행됩니다. 최근 10건은
전부 국내 상용 소프트웨어입니다 — ipTIME 공유기, 한컴오피스, 알집, 지니언스 NAC, 나다텔 DVR,
한비로 그룹웨어. Go·npm·PyPI·Alpine 패키지는 하나도 없습니다. 컨테이너 이미지나 Go 모듈 트리에
대한 CVE ID 조인은 사실상 한 번도 걸리지 않습니다.

레코드의 *품질*은 이 슬라이스가 가정했던 것보다 낫습니다. 각 항목이 CVE ID, CVSS 점수와 등급,
영향받는 버전과 해결 버전, CWE, 한국어 설명을 담습니다. 장애물은 형식이 아닙니다. 대상 영역과
assay의 타깃이 거의 겹치지 않는다는 것입니다.

**KVE 식별자는 존재하지만, 포털에서 그것으로 조회되는 것이 없습니다.** §1이 KVE를 이 프로젝트가
존재하는 이유의 일부로 지목하므로 따로 확인했습니다.

KVE는 실재합니다. KISA가 번호를 부여하고, 제3자가 구체적인 번호를 인용합니다 — 한 네트워크 장비
업체의 패치 공지가 `KVE-2023-6187`을 참조하고, 버그바운티 정리 페이지들이 `KVE-2024-0770`,
`KVE-2024-0771`을 나열합니다. 찾지 못한 것은 그 번호로 조회되는 KNVD 공개 레코드입니다. 포털
자체의 통합검색으로 측정했습니다.

| 질의 | 공지사항 | 보안공지 | 공개된 취약점 |
|---|---|---|---|
| `KVE-2024-0771` | 0 | 0 | 0 |
| `KVE` (문자열 자체) | 0 | 0 | 0 |
| `CVE-2026-24498` *(대조군)* | 0 | 0 | **1** |

대조군이 중요합니다. 그것이 없으면 0건은 검색이 고장 난 것과 구분되지 않습니다. 검색은
동작하며, `KVE`라는 문자열은 포털의 공개 콘텐츠 어디에도 나오지 않고, 공개된 모든 레코드는 CVE를
제목과 키로 씁니다(`CVE-2026-24498 | EFM-Networks ipTIME …`).

맞아떨어지는 해석은 이렇습니다. KVE 번호는 신고 처리 절차(신고 → 분석·검증 → 개발사 전달)에서
부여되어 서신과 업체 패치 공지에 실려 다니고, 포털은 CVE로 공개합니다. 2차 자료들은 여전히 KVE를
"KNVD에서 확인 가능"하다고 설명하지만, 포털이 재구축되면서 `resultList.do`, `detailSecNo.do`,
`rewardExplain.do`가 모두 오류를 반환하므로 그 설명들은 재구축 이전을 가리킬 수 있습니다.

**확인하지 못한 것:** 이전 포털이 KVE 레코드를 공개했는지, 로그인 계정에서는 보이는지, KVE→CVE
매핑이 어딘가 조회 가능한 형태로 있는지. 각각 KISA에 직접 문의해야 알 수 있습니다.

**설계에 대한 함의.** §1의 전제는 쓰인 그대로 성립합니다 — KISA는 KVE 식별자를 발행합니다 —
다만 D3의 `Aliases`/`Upstream` "CVE↔KVE 조인"은 오늘 기준 조인할 공개 KVE 쪽이 없습니다. 그
조인은 하중을 받지 않습니다. 두 필드를 모두 읽어야 한다는 것은 *OSV 안에서* 독립적으로 확인된
사실이고(Go 레코드는 `aliases`에, Alpine 레코드는 `upstream`에 CVE를 담습니다), D3은 KVE와
무관하게 자기 근거로 성립합니다.

**접근 경로.** 문서화된 RSS 피드가 둘 있습니다 — `/rss/security/notice`와
`/rss/security/info` — 그리고 각각 **최신 10건만** 반환하며, 전량 내보내기도 날짜 범위도
페이지네이션도 없습니다. 사이트는 문서화되지 않은 POST API(`/api/core/pu/view/…`)가 떠받치는 Vue
SPA이고 그쪽은 페이지네이션이 되지만 **공개된** 인터페이스는 아닙니다. 포털이 최근 재구축되면서
이전 딥링크(`detailSecNo.do?IDX=…`)가 서버 오류를 반환하므로, 애초에 안정된 계약이라고 볼 근거가
없었습니다. 공공데이터포털에서 대응하는 데이터셋을 찾지 못했습니다. `internal/provider/knvd`는
바로 그 불안정성을 가정하지 않고 견디도록 만들어져 있습니다 — 모든 페이지에 대한 `resType` 확인
(위의 count 엔드포인트·빈 목록 발견), `skipCount`를 더 이상 따르지 않는 서비스를 잡아내는
반복-첫-ID 가드, 확실히 영구적이지 않은 것은 전부 일시적으로 취급하는 재시도 정책입니다.

**약관.** 사이트 푸터는 `Copyright(C) 2026 KISA. All rights reserved.`이고 공공누리 표시가
없습니다. 재사용을 허용하는 공공기관은 공공누리 유형을 표시하며, 그 표시 없이 모든 권리 보유 문구만
있는 것은 허용이 아닙니다. 이것을 푸는 것이 D29입니다. 그 문제가 풀리기 전까지는 로컬에서만 만들고
배포 전에 벗겨냅니다.

**2026-08-05에 나왔습니다.** `internal/provider/knvd`가 공지를 받아오고, `internal/advisory`와
`enrichment` 버킷(스키마 7)이 한 공지가 지목하는 CVE마다 레코드 하나씩을 담으며,
`Matcher.annotate`가 NVD의 rating과 정확히 같은 방식으로 CVE를 기준 삼아 finding에 그것을
붙이고, table과 `--explain`과 JSON이 모두 그것을 보여줍니다. `KISA_ENABLE`이 `db build`에서 그
fetch를 게이팅하는 것은 `NVD_ENABLE`과 같은 모양입니다. 처음부터의 D3이 끝까지 그대로
유지됐습니다. 보강은 판정도, 심각도도, 종료 코드도 바꾸지 않습니다 — 그것은 독자를 위한 산문일
뿐입니다.

**KNVD가 독립 매칭 소스가 될 수 있는지는 assay의 타깃이 컨테이너 이미지와 소스 트리가 아니라
호스트나 워크스테이션을 포함하게 될 때 다시 봅니다.** 그때가 한컴오피스와 ipTIME 펌웨어가 스캔에
걸릴 수 있는 대상이 되는 시점이고, `docs/deferred-decisions.md`가 그 질문을 위해 이미 기록해 둔
것과 같은 트리거입니다. 그 질문은 보강과는 별개이고 여전히 열려 있습니다. 보강 자체는 그것을
기다리지 않고, 이미 사용자가 있습니다.

### 첫 전체 코퍼스 빌드, 2026-08-05

슬라이스 ⑦·⑧·⑤를 머지한 뒤 처음으로 함께 돌렸습니다. CI가 아니라 빌드 서버에서, 모든 창을
풀어놓고: **6시간 31분**, advisory 32,272건, NVD는 **354,067**건의 등급이 붙은 CVE로 피드
전체, KISA는 공지 2,971건에서 뽑은 보강 레코드 **18,523**건, 디스크에서 256MB.
`ghcr.io/kun9497/assay-db:v7`로 배포했습니다.

테스트로는 잴 수 없던 것 세 가지를 이 실행이 쟀습니다.

- **타임아웃 수정이 결정적이었습니다.** 그 앞의 실행은 3시간 50분, 262,000 레코드 지점에서
  클라이언트 타임아웃을 영구 실패로 분류해 죽었습니다 — `net/http`의 `timeoutError.Is`가
  `context.DeadlineExceeded`에 대해 참을 돌려주기 때문에 deny-list가 그것을 치명으로
  통과시켰습니다. v7 실행은 같은 계열을 한 번 만났고(HTTP/2 `stream error`) **5초** 만에
  회복했습니다. 같은 실패가 수정 전에는 116분, 수정 후에는 5초였습니다.
- **D29가 테스트가 아니라 실제 아티팩트에서 지켜집니다.** 배포된 레이어를 빈 디렉터리로 다시
  받아 바이트로 읽었습니다. 로컬 빌드는 한글 시퀀스 **1,719,126**개와 `knvd.krcert.or.kr`
  18,524회를 담고 있고, 배포된 아티팩트는 둘 다 **0**입니다. 위의 6번 경로가 무력화했던 바로 그
  검사를, 사용자가 실제로 내려받는 파일에 대고 돌린 것입니다.
- **받아온 아티팩트로 스캔한 결과가 한국어가 없다는 점만 빼고 동일합니다** — 같은 finding, 같은
  band, `--fail-on critical|high|medium|low` 전체에서 같은 종료 코드. D3의 "보강은 판정을 바꾸지
  않는다"가 이제 단위 테스트가 아니라 끝에서 끝까지 확인됐습니다.

### 슬라이스 9 — comparer가 읽지 못하는 버전 ← 다음

버전이 파싱되지 않는 패키지는 **건너뜀**으로 보고되고 깨끗한 판정에 섞이지 않습니다(D20, D21).
따라서 이것은 조용한 실패가 아니라 시끄러운 실패입니다. 그래도 판정을 받지 못한 취약점인 것은
사실이고, D9이 바로 그렇게 말합니다 — *파싱할 수 없는 버전을 "취약하지 않음"으로 처리하는 것은
놓치는 것이다.*

2026-08-06, v7 데이터베이스를 대상으로 측정했습니다. 모든 advisory의 모든 범위 경계를 그 생태계를
담당하는 comparer에 넣었습니다.

| comparer | 파싱 못 하는 경계 | 전체 경계 | 패키지 |
|---|---:|---:|---:|
| semver (Go, npm) | 96 | 29,840 | 42 |
| pep440 (PyPI) | 45 | 31,147 | 14 |
| apk (Alpine) | 61 | 53,819 | 30 |

전체의 0.18%이고, 원인은 이국적이지 않습니다. 지배적인 모양은 **문법이 요구하는 것보다 자릿수가
적은 버전**입니다 — `github.com/canonical/lxd`의 `4.0`·`6.0`·`6.5`, `next`의 `13.0`,
`github.com/cosmos/cosmos-sdk`의 `0.46`. semver는 세 자리를 요구하는데 상류의 advisory 본문은
흔히 두 자리로 씁니다. 나머지는 진짜 별종입니다 — `libdwarf`의 `1999-12-14`(날짜),
`buildbot`의 `0.7.11p3`, `neutron`의 `7.2.0-12.1`.

같은 날 실제 스캔에서 두 건을 만났습니다. `alpine:3.14`가 `libretls 3.3.3p1-r3`을 건너뛰었고 그와
함께 CVE-2022-0778도 건너뛰었습니다. assay 자신의 바이너리를 스캔할 때는 GHSA 범위 경계가
`19.03.0`이라 `github.com/docker/cli`를 건너뛰었는데, 그 `03`이 semver가 금지하는 선행 0 숫자
식별자입니다.

**열린 질문은 생태계별 관용이고, D9이 그것을 셋에 대해 한 번에 답하는 것을 금지합니다.** semver
생태계에서 `4.0`을 `4.0.0`으로 읽어도 되는지, Alpine 자신의 패키지 버전이 apk-tools도 그렇게
한다고 시사하는 대로 apk가 문자 뒤의 숫자(`3.3.3p1`)를 받아들여야 하는지, pep440이 `p3` 패치
접미사를 받아들여야 하는지는 상류 권위가 각각 다른 세 개의 질문입니다. 각각 자기 결정, 자기
table-driven 케이스, 그리고 그 생태계가 공개한 벡터에 대한 자기 검증이 필요합니다 — apk
comparer는 이미 apk-tools의 738개 비교를 통과해 서 있고, 그것이 기준선입니다. 공유된 "관대하게
하자" 규칙 하나가 정확히 D9이 막으려는 붕괴입니다.

여기서 무엇도 버전을 오늘보다 **낮게** 비교되게 만들어서는 안 됩니다. 고치려는 실패가 놓침이고,
이미 올바르게 처리되던 버전의 순서를 뒤집는 관대한 파싱은 시끄러운 놓침을 조용한 놓침으로
바꾸는 거래이기 때문입니다.

### 슬라이스 10 — 어느 KISA 공지가 이기는가

2026-08-06, 처음 실제로 써 보면서 발견하고 v7 데이터베이스로 측정했습니다. 결함 둘, 원인 하나.

**저장소가 동점을 도착 순서로 해결하는데, D25가 그것을 금지합니다.** 보강 버킷은
`(CVE, Source)`로 키가 잡히고 모든 KISA 레코드의 source가 같으므로, 공지 둘이 지목한 CVE는 나중에
도착한 쪽만 남습니다. 빌드 자신의 로그가 그 숫자를 갖고 있었습니다. `convert`가 **20,314**건을
내보냈고 저장소는 **18,523**건을 지켰으니, **1,791**건이 페이지 순서로 덮였습니다. D25가 등급에
대해 이미 정리한 문제입니다 — *동점을 도착 순서로 해결하지 말 것. 그것이 결함이었지, 무해한 동전
던지기가 아니었다* — 그리고 보강 버킷이 그것을 되풀이했습니다.

**공지 대부분이 월간 롤업이고, 그것들이 물량으로 그 동점을 이깁니다.** 서로 다른 공지 1,935건 중
804건은 정확히 CVE 하나를 지목하지만, 38건은 백 개가 넘게 지목하고
`MS 7월 보안 위협에 따른 정기 보안 업데이트 권고` 하나가 **1,046**개를 지목합니다. 저장된 18,523건
중 **12,997건(70%)** 이 20개 초과를 주장하는 공지에서 나왔습니다. 실제 스캔에서 만난 보강된
finding은 전부 — `node:14-alpine`의 `openssl` CVE-2024-5535, `nginx:1.25.3-alpine`의 `curl`
CVE-2024-6197 — 마이크로소프트 월간 패치 공지를 마이크로소프트와 무관한 취약점에 붙였습니다. 이
기능을 가질 값어치가 있게 만드는 구체적인 공지들은 분명히 존재하지만(regreSSHion에 대한
`OpenSSH 제품 보안 업데이트 권고`, CVE-2024-3094에 대한 `XZ-Utils 보안 주의 권고`,
`BIND DNS 취약점 보안 업데이트 권고`), 같은 CVE를 롤업도 지목하면 그때마다 집니다.

유력한 규칙은 **가장 좁은 공지가 이긴다**입니다 — 주장하는 CVE 수가 가장 적은 쪽, 동수면 두 실행이
일치하도록 공지 ID로 결정 — 이것이 도착 순서 의존과 롤업 희석을 한꺼번에 없앱니다. 세 번째 결함이
여기 얹혀 옵니다. 2,202건(12%)의 요약이 `□ 개요` 제목을 찾지 못해 `제목없음` 폴백에서
시작합니다.

보강은 판정을 바꾸지 않으므로(D3) 이 중 무엇도 틀린 답을 만들어내지는 못합니다. 그래서 슬라이스
9보다 앞이 아니라 뒤에 놓았습니다.

## 5. 검증

**grype와의 대조 테스트가 주 정확성 검증 수단**이며, 매 슬라이스마다 반복합니다. 같은 SBOM 또는
이미지를 두 도구에 넣고 결과를 비교합니다.

완전한 일치는 기대하지 않습니다. 데이터 소스가 다르니까요. 신호는 **차이의 크기**입니다. 큰 차이가
난다면 우리 매처가 틀린 것입니다. **가장 싸면서 가장 강한 정답지**이고, 돌리는 데 비용이 들지
않습니다.

그 외:

- `Store`가 인터페이스이므로 `Matcher`는 인메모리 fake로 테스트합니다 — 매칭 로직을 검증하는 데
  데이터베이스가 필요 없습니다.
- **`Comparer`의 테스트 밀도가 가장 높아야 합니다.** 생태계별 표 기반으로 deb epoch, apk `-rN`
  접미사, semver pre-release 우선순위, PEP 440 `.post` / `.dev`를 다룹니다. **여기가 미탐의
  발원지입니다.**
- bbolt 구현체는 작은 fixture 데이터베이스로 별도 테스트합니다.

## 6. 벤치마킹 노트

기존 도구에서 가져온 설계 요소와, 남겨둔 것.

**trivy에서**

- 데이터베이스를 OCI 아티팩트로(`ghcr.io`) — 레지스트리 배포를 쓰면 미러링·인증·에어갭 대응이
  공짜로 따라옵니다. *미룸. deferred-decisions 참조.*
- 로컬 store로 bbolt — 같은 접근 패턴, 같은 결론. *채택(D4).*
- 선택적 데이터를 별도 아티팩트로 분리(`trivy-java-db`) — KISA 데이터에 대응됩니다. *미룸.*
- 수집한 업스트림 데이터를 git에 커밋(`vuln-list`)해 감사 추적 확보. *미룸.*
- **가져오지 않은 것:** 설정·시크릿·IaC·쿠버네티스 스캔으로의 범위 확장.

**grype에서**

- 소스 패키지를 통한 간접 매칭. *채택(D8) — 이건 미탐을 막는 것이라 처음부터 들어갑니다.*
- 스키마 버전을 디렉터리로, 마이그레이션 대신 재빌드. *채택(D5).*
- assay는 인벤토리까지 만들지만, 내부 경계는 "SBOM in, findings out"의 깔끔함을 따름.
  *채택 — §3의 모양이 그것입니다.*
- **가져오지 않은 것:** 우리가 소유하지 않은 데이터베이스 스키마에 의존하는 것. 그러면 KISA가
  막힙니다.
