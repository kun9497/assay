# QA 2026-11-02 — full-source audit and fixes

English canonical · [한국어](2026-11-02-qa-audit.ko.md)

A read-only audit of `main` at `d2f894f` (v0.14.0 plus #223 and #224), run the same day as
the release, across six dimensions, with every finding put through an independent
refutation pass before it was accepted. 25 findings came back; 24 survived refutation and
every one of the 24 has a fix merged or in a PR named below. This document records what was
checked, what was found, what was fixed and how, and what remains to watch.

## 1. Scope and method

**Baseline.** `origin/main` at `d2f894f`, the merge of #224. Nothing was released, published
or deployed by the audit itself; the fixes are ordinary PRs.

**Dimensions**, one reader each, read-only on the repository (probe tests built into a
scratch directory, never into the tree):

| # | Dimension | What it pressed on |
|---|---|---|
| 1 | Matcher and comparers | every `Comparer` against its reference algorithm (90 adversarial pairs), `AffectsVersion` / `InRange`, grouping, D8 source lookup, lineage gating, `Package.Source` population |
| 2 | Providers and data | every provider's OSV conversion, fix states, D16/D15, delta-vs-archive precedence, D12 `DataAsOf`, `db push` guards, D110/D115 carry, D137/D150 trust, the D159 change against 53 live SUSE documents |
| 3 | Scan path and CLI contract | exit precedence 2 > 1 > 0, stream discipline on every exit path, schema 16 vs `docs/compatibility.md`, SARIF rule declaration, skip accounting, the air-gap paths, the layer walk |
| 4 | Wrong information | every user-facing string, help text vs parser, README / DESIGN / compatibility / deferred-decisions / CHANGELOG EN and KO, CLAUDE.md's "since Dnnn" clauses |
| 5 | Service and operations | the workflows, scripts, installers, `cmd/dbstatus`, `cmd/scandiff` gate semantics, push / pull / trust failure modes |
| 6 | Input security | tar and layer handling, rpm database parsers under mutation (9,000 mutated databases, 50,000 random headers), jars, SBOM and lockfile decoders, trust verification order, credentials, platform parsing, the OpenVEX and `.assay.yaml` readers |

**Verification.** Each finding was handed to a second agent told to refute it against the
code, with "default to not real if uncertain". One was refuted (a typo'd path falling through
to the registry loader is the recorded D22 choice, with disclosure as its mitigation). Severity
is the audit's scale: **P1** a silent wrong verdict or wrong published data, **P2** wrong
information shown to a user or operator, **P3** everything else worth fixing.

**Fixing.** Each fix followed the project's rules: the caller's test first, red on the
unfixed code; the fix; mutation rounds on the committed baseline; an independent adversarial
review of the PR with its own refutation pass; CHANGELOG and every touched document in both
languages in the same commit; no new D number, a **Revised (QA 2026-11-02)** paragraph under
the decision instead. Review findings were folded into the PRs before merge.

## 2. Findings

### P1 — silent wrong verdicts

| # | Where | Defect | Fix |
|---|---|---|---|
| 1 | `internal/pkgmeta/distropurl.go` | The SBOM readers kept only the NAME half of a deb purl's `upstream=<source>@<version>` and of an rpm purl's SRPM name, so D41 and D153 never applied to CycloneDX or SPDX input: bsdutils `1:2.38.1-5+deb12u3` from util-linux `2.38.1-5+deb12u2` was one finding on the image path and zero findings, zero skips, exit 0 as an SBOM. | #233: the deb version half is kept; the rpm SRPM version is kept and the D152/D153 epoch pass runs over the document's rpm packages; CycloneDX also reads `syft:metadata:sourceVersion`; a source-scoped VEX statement now reaches the source version. |
| 4 | `internal/provider/redhat/csaf.go` | The Hummingbird purl reader stopped at `?` and discarded the `epoch=N` qualifier. nginx (epoch 2) and tomcat10/11 (epoch 1) were stored fixed at `1.30.4-2.hum1` while rpmdb reads the installed build as `2:1.30.4-1.hum1`; the RPM comparer orders the epoch first, so every vulnerable epoch-carrying Hummingbird build was reported clean. 67 of 403 distinct Hummingbird purls in the 160 newest documents carry an epoch. | #235: both CSAF readers parse the purl with `pkgmeta.ParsePURL` and prefix a non-zero epoch, the rule the scan side already applied; counters show epoch-carrying leaves in the nightly line. |
| 6 | `internal/cataloger/spdx/spdx.go` | The DESCRIBES target was dropped before cataloging, unconditionally and only the first one, so a document describing the one real package it inventories scanned as "The document contained no components." with exit 0 under `--fail-on low --fail-on-incomplete`. The project's own `tiny.spdx.json` fixture had a test asserting the defect. | #230: every DESCRIBES target is cataloged into a scratch and dropped uncounted only in the pseudo-package shapes (no purl, every purl `pkg:oci`, a versionless purl); any other described entry is a candidate or a counted skip like its undescribed twin. |

## 3. What was checked and found correct

The audit's own list, abridged. Every comparer ordered 90 adversarial pairs as its reference
algorithm does. The union-of-ranges evaluation, highest clearing fix, D154 tie ordering and the
D30 enumerated-list fallback behaved on every well-formed shape. D16 and D15 hold at ingestion;
Red Hat and SUSE fix states map as their decisions say; D129/D135 precedence holds in both CSAF
providers; every provider opens its ranges with `{Introduced: "0"}`; the D159 change named only
real rpm binaries across 53 live documents. Exit precedence, stream discipline (stdout held zero
bytes on every exit-2 path probed), schema 16 against the compatibility page, SARIF rule
declaration (41 rules, 41 used), and the air-gap paths (only the registry branch imports a
network client) all held. The signing chain verifies before anything is written or parsed; the
v0.14.0 release ran its toolchain floor and six vulncheck hooks before publishing; `install.sh`
verified the real release from this machine. No panic was reachable from crafted tars, rpm
databases, versions or purls.

## 4. Follow-ups, not done here

- **Watch the first nightly after #235 merges**: the published artifact's Hummingbird nginx and
  tomcat records carry no epoch until it rebuilds; grype-only tuples on the `hummingbird`
  scandiff target would be the trace of the old records.
- **Watch the first two nightlies on `17 5 * * *`** against the 05:20Z–13:00Z window DESIGN now
  promises, and the 2026-11-09 weekly on `23 20 * * 0`. The Monday review routine (outside the
  repository) must stay at least three hours after the weekly cron; 01:30 UTC is fine.
- **`timeout-minutes: 15` on the three status jobs** is sized from what they do; the first slow
  runner will say whether it needs headroom.
- **The Monday routine's prompt** still infers bridge growth from the table's shape; it can now
  read `A_BRIDGED` directly (#225).
- **D153 step 4 on SBOM input**: an SBOM listing mod_ssl with no other package from its SRPM
  keeps the binary's epoch, pinned as a residual; preferring "no epoch" when the document states
  none would be a D153 revision.
- **Fix-state wording for the D134 source substitution** on the skip path mirrors the hit path's
  annotation only in part; a readability follow-up, pre-existing.
- **The Windows `ECONNRESET` clause** in the three providers' retry helpers never matches a live
  reset on Windows (Go's synthetic errno vs WSAECONNRESET); Linux-only by construction, where the
  nightlies run.
